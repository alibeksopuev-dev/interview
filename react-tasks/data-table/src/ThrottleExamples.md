# Разбор ThrottleExamples.tsx — построчный анализ

## Что такое throttle?

Throttle — это техника ограничения частоты вызовов функции.
Принцип: первый вызов проходит **сразу**, все последующие вызовы в течение заданного времени **блокируются**.

Пример: пользователь скроллит страницу и браузер стреляет 30 событий за секунду. Без throttle твой код будет перерисовывать UI 30 раз. С throttle(fn, 200) — максимум 5 раз в секунду.

## Часть 1 — хук `useThrottledValue` (строки 7–24)

```tsx
export function useThrottledValue<T>(value: T, wait: number): T {
```
Обобщённый (generic) хук. Принимает любое значение `value` и задержку `wait` в миллисекундах.
Возвращает то же значение, но обновляющееся не чаще чем раз в `wait` мс.

```tsx
const [throttledValue, setThrottledValue] = useState(value)
```
Локальное состояние — это "замедленная копия" входного значения.
Изначально равна исходному значению.

```tsx
const setter = useRef(
  throttle((v: T) => {
    setThrottledValue(v)
  }, wait)
).current
```
Здесь происходит ключевая вещь — **один раз** при монтировании компонента создаётся throttled-функция и кладётся в `useRef`.

Почему `useRef`?
- `useRef` не вызывает перерендер при изменении
- Значение внутри `.current` живёт всё время жизни компонента
- Если бы мы написали просто `throttle(...)` без `useRef` — при каждом рендере создавалась бы **новая** throttle-функция с обнулённым таймером, и throttle бы не работал

`.current` в конце — сразу достаём значение из ref, чтобы не писать `setter.current()` при каждом вызове.

```tsx
useEffect(() => {
  setter(value)
}, [value, setter])
```
Когда входное `value` меняется — вызываем throttled setter.
`setter` в зависимостях потому, что ESLint требует указывать все переменные из closure. На практике `setter` никогда не меняется (он в `useRef`).

```tsx
return throttledValue
```
Возвращаем замедлённое значение. Компонент снаружи получает значение, которое обновляется реже.

## Часть 2 — `ScrollTracker` (строки 29–88)

**Задача:** показать разницу между реальными событиями скролла и throttled-обновлениями.

```tsx
const [scrollY, setScrollY] = useState(0)       // throttled позиция
const [realScrollY, setRealScrollY] = useState(0) // реальная позиция
const [throttleCount, setThrottleCount] = useState(0) // сколько раз сработал throttle
const [realCount, setRealCount] = useState(0)   // сколько раз браузер стрельнул событием
```
Четыре счётчика для визуального сравнения "сырые события vs throttled".

```tsx
const handleScrollThrottled = useRef(
  throttle((y: number) => {
    setScrollY(y)
    setThrottleCount(c => c + 1)
  }, 200)
).current
```
Throttled обработчик с задержкой 200 мс. Та же идея с `useRef` — функция создаётся один раз.
Внутри: обновляем throttled-позицию и увеличиваем счётчик throttled-вызовов.

```tsx
const handleScroll = (event: UIEvent<HTMLDivElement>) => {
  const currentScrollY = event.currentTarget.scrollTop
  setRealScrollY(currentScrollY)  // обновляем ВСЕГДА
  setRealCount(c => c + 1)        // считаем ВСЕ события
  handleScrollThrottled(currentScrollY) // throttle решает, обновить ли state
}
```
Это обычный (не throttled) обработчик. Он:
1. Берёт текущую позицию скролла из события
2. Всегда обновляет "реальные" данные — чтобы показать сколько событий реально было
3. Передаёт позицию в throttled функцию — та решит, пропустить или заблокировать

```tsx
<div className="scroll-box" onScroll={handleScroll}>
  {[...Array(50)].map((_, i) => (
    <div key={i} className="scroll-item">Элемент списка #{i + 1}</div>
  ))}
```
Создаём 50 элементов чтобы был скролл. `[...Array(50)]` — быстрый способ создать массив из 50 пустых слотов.

## Часть 3 — `SubmitButton` (строки 99–203)

**Задача:** защита кнопки от спам-кликов. Первый клик проходит, следующие 2 секунды — блокируются.

```tsx
interface LogEntry {
  id: string
  time: string
  status: 'allowed' | 'ignored'
}
```
Тип для записи в лог. `status` — либо "пропущен", либо "заблокирован".

```tsx
const throttledSubmit = useRef(
  throttle(() => {
    const now = new Date()
    const timeStr = now.toTimeString().split(' ')[0] + '.' + String(now.getMilliseconds()).padStart(3, '0')
    setLogs(prev => [
      { id: Math.random().toString(36).substr(2, 9), time: timeStr, status: 'allowed' },
      ...prev.slice(0, 7), // не больше 8 записей в логе
    ])
  }, 2000)
).current
```
Throttled функция "отправки". Задержка 2000 мс (2 секунды).

Разбор строки времени:
- `now.toTimeString()` → `"14:32:05 GMT+0600 (...)"`
- `.split(' ')[0]` → `"14:32:05"`
- `+ '.' + String(now.getMilliseconds()).padStart(3, '0')` → `"14:32:05.047"`

`Math.random().toString(36).substr(2, 9)` — генерация короткого случайного id (base36 = цифры + буквы).

`prev.slice(0, 7)` — берём первые 7 из предыдущих записей, добавляем новую → итого максимум 8 в списке.

```tsx
const handleClick = () => {
  setClickCount(c => c + 1)
  const prevLogsLength = logs.length
  throttledSubmit()
```
При клике: считаем клик, запоминаем текущую длину лога, вызываем throttled submit.

```tsx
  setLogs(prev => {
    const hasJustAllowed = prev.length > prevLogsLength 
      && prev[0].status === 'allowed' 
      && prev[0].time === timeStr
    if (!hasJustAllowed) {
      return [{ id: ..., time: timeStr, status: 'ignored' }, ...prev.slice(0, 7)]
    }
    return prev
  })
```
Логика определения "был ли клик заблокирован":
- Если `throttledSubmit()` выполнился → лог вырос (`prev.length > prevLogsLength`) и первый элемент — `allowed`
- Если throttle заблокировал → лог не изменился → добавляем запись `ignored`

Это хак для визуализации: throttle не возвращает "пропущен/нет", поэтому смотрим на изменение стейта.

## Часть 4 — `ResizeAwareComponent` (строки 208–285)

**Задача:** показать throttle при отслеживании размеров — окна браузера и локального элемента.

```tsx
const [windowWidth, setWindowWidth] = useState(window.innerWidth)
```
Начальное значение — текущая ширина окна при монтировании компонента.

```tsx
useEffect(() => {
  const handleResize = () => setWindowWidth(window.innerWidth)
  window.addEventListener('resize', handleResize)
  return () => window.removeEventListener('resize', handleResize)
}, [])
```
Подписка на событие `resize` окна.
`return () => removeEventListener(...)` — это cleanup функция: вызывается при размонтировании компонента, чтобы не было утечки памяти.

```tsx
const throttledWindowWidth = useThrottledValue(windowWidth, 300)
```
Используем наш хук из части 1. `windowWidth` меняется на каждый пиксель — `throttledWindowWidth` не чаще раза в 300 мс.

```tsx
const observer = new ResizeObserver(entries => {
  for (let entry of entries) {
    setLocalWidth(entry.contentRect.width)
  }
})
observer.observe(resizeBoxRef.current)
return () => observer.disconnect()
```
`ResizeObserver` — браузерный API, следит за размером конкретного DOM-элемента (в отличие от `resize` события, которое только для окна).
`observer.disconnect()` в cleanup — отписываемся при размонтировании.

```tsx
const throttledLocalWidth = useThrottledValue(localWidth, 300)
```
То же самое: реальная ширина обновляется часто, throttled — раз в 300 мс.

## Часть 5 — `RafTracker` (строки 290–371)

**Задача:** сравнить `requestAnimationFrame` (rAF) и throttle для отслеживания мыши.

```tsx
const rafIdRef = useRef<number | null>(null)
const pendingPosRef = useRef({ x: 0, y: 0 })
```
- `rafIdRef` — хранит ID текущего запроса rAF (нужен чтобы отменить предыдущий)
- `pendingPosRef` — хранит последнюю позицию мыши (не вызывает ререндер!)

```tsx
const throttledSetPos = useRef(
  throttle((pos: { x: number; y: number }) => {
    setThrottledPos(pos)
  }, 100)
).current
```
Throttled обновление позиции: не чаще раза в 100 мс.

```tsx
const handleMouseMove = (e: React.MouseEvent<HTMLDivElement>) => {
  const rect = e.currentTarget.getBoundingClientRect()
  const pos = {
    x: Math.round(e.clientX - rect.left),
    y: Math.round(e.clientY - rect.top),
  }
```

#### Глубокий разбор расчета координат мыши:

Этот паттерн используется повсеместно, когда нужно узнать, в каком конкретно месте **внутри нашего элемента** находится курсор мыши.

1.  **Что делает `e.clientX` и `e.clientY`?**
    Это глобальные координаты курсора мыши в пикселях **относительно видимого окна браузера (viewport)**.
    *   Если курсор находится в самом левом верхнем углу экрана монитора (окна браузера), то `clientX === 0` и `clientY === 0`.
    *   Эти координаты никак не привязаны к элементам на странице. Если вы прокрутите страницу, элемент уедет, но `clientX` у левого угла экрана останется нулем.
2.  **Что делает `e.currentTarget.getBoundingClientRect()`?**
    Этот метод возвращает объект с геометрическими размерами нашего элемента (в данном случае контейнера, по которому двигают мышь) и его текущим положением на экране:
    *   `rect.left`: Расстояние от левого края экрана до левого края нашего элемента.
    *   `rect.top`: Расстояние от верхнего края экрана до верхнего края нашего элемента.
    *   `rect.width` и `rect.height`: Ширина и высота элемента.
3.  **Математика: `e.clientX - rect.left`**
    Чтобы перевести координаты мыши из глобальных (относительно окна) в локальные (относительно самого элемента), мы вычитаем отступы элемента от краев экрана:
    *   **Пример:** Наш контейнер расположен по центру экрана. Его левый край отступает от левого края окна браузера на `300` пикселей (`rect.left = 300`).
    *   Мы навели мышь ровно на левый край нашего контейнера. `clientX` в этот момент будет равен `300`.
    *   Считаем локальный `X`: `clientX - rect.left` $\rightarrow$ `300 - 300 = 0` (мышь ровно на левой границе элемента!).
    *   Сдвинули мышь вправо на `50` пикселей внутрь контейнера. `clientX` стал `350`.
    *   Локальный `X`: `350 - 300 = 50` пикселей относительно контейнера.
4.  **Зачем нужен `Math.round`?**
    Браузер может возвращать дробные координаты (особенно на Retina/высокоплотных экранах или при масштабировании страницы). Округление `Math.round` гарантирует чистые целые числа пикселей для корректного позиционирования HTML/CSS-элементов.

```tsx
  setRawCount(c => c + 1)
  pendingPosRef.current = pos  // сохраняем последнюю позицию в ref (без ререндера!)
  throttledSetPos(pos)         // throttle обновляет стейт (с ограничением)
```
Счётчик сырых событий растёт при каждом движении мыши.
Позиция сохраняется в `ref` — это "буфер" для rAF.

```tsx
  if (rafIdRef.current !== null) cancelAnimationFrame(rafIdRef.current)
  rafIdRef.current = requestAnimationFrame(() => {
    setRafPos(pendingPosRef.current)  // берём ПОСЛЕДНЮЮ позицию из буфера
    setRafCount(c => c + 1)
    rafIdRef.current = null
  })
```
Паттерн "отменить предыдущий rAF и поставить новый":
- Если мышь движется быстро и два события пришли до следующего кадра — отменяем старый rAF, ставим новый
- Итог: rAF всегда берёт **последнюю** позицию и выполняется синхронно с перерисовкой браузера (~60 fps = ~16 мс)

**Разница между rAF и throttle(100):**
- throttle(100) — жёсткий таймер. Обновляет позицию раз в 100 мс вне зависимости от кадров браузера
- rAF — синхронизирован с монитором. Обновляет ровно перед каждой перерисовкой (~16 мс на 60hz)
- rAF лучше для анимаций, throttle лучше для API-запросов и тяжёлых вычислений

```tsx
useEffect(() => {
  return () => {
    if (rafIdRef.current !== null) cancelAnimationFrame(rafIdRef.current)
  }
}, [])
```
Cleanup: при размонтировании отменяем pending rAF чтобы не было обращения к размонтированному компоненту.

Что означают эти показатели?
Сырые события (Raw events) — 573 mousemove всего

Что это: Общее количество событий движения мыши (mousemove), которые сгенерировал браузер, пока вы водили курсором в интерактивной зоне.
Суть: Браузер генерирует события mousemove с очень высокой частотой (зависит от частоты опроса вашей мыши, часто до 120-250+ раз в секунду). Обрабатывать каждое такое событие "в лоб" для сложных операций — крайне неэффективно.
Throttle (100мс) — координаты 200, 133 (каждые 100мс)

Что это: Координаты ($X, Y$ в пикселях) положения курсора, которые были зафиксированы и обработаны функцией с ограничением частоты (throttle).
Суть: Функция обновления срабатывает не чаще одного раза в 100 мс (максимум 10 раз в секунду).
rAF (~16мс) — координаты 161, 161, кадров: 542

Что это: Координаты ($X, Y$) курсора, обновляемые с помощью requestAnimationFrame (rAF).
Кадров (542): Количество раз, когда функция rAF успешно обновила позицию на экране.
Суть: rAF привязывается к частоте обновления вашего монитора (для экрана 60 Гц это примерно каждые 16.6 мс). Он гарантирует, что позиция обновится ровно перед тем, как браузер начнет перерисовывать экран.
Какие выводы можно сделать?
1. Оптимизация производительности (Пропуск "лишней" работы)
Из 573 сырых событий движения мыши rAF выполнил 542 обновления.
В то же время Throttle (100мс) выполнил значительно меньше обновлений. Если предположить, что 542 кадра на частоте 60fps заняли около 9 секунд, то throttle обновил состояние всего ~90 раз!
Вывод: Оба подхода отлично снижают нагрузку на процессор и избавляют от лишних рендеров React по сравнению с обработкой «сырых» событий. Однако степень экономии ресурсов у них разная.
2. Разница в визуальной точности и задержке (Coordinate Lag)
Обратите внимание на координаты в момент скриншота:
rAF: 161, 161 (самая свежая и актуальная позиция курсора).
Throttle: 200, 133 (устаревшая позиция курсора, зафиксированная на предыдущем 100-миллисекундном шаге).
Вывод: Throttle дает заметную задержку (lag) в визуальном отклике. Если использовать throttle для отрисовки кастомного курсора или перетаскивания (Drag & Drop), движение элемента будет казаться дерганым и отстающим от реальной мыши. rAF же обновляется синхронно с монитором, поэтому движение выглядит идеально плавным.
Резюме: когда что использовать?
Используйте requestAnimationFrame (rAF), когда вам нужна идеальная визуальная плавность в реальном времени:

Кастомные курсоры (как в этой демке).
Drag & Drop интерфейсы.
Анимации, привязанные к прокрутке (parallax) или движению мыши.
Отрисовка на Canvas.
Используйте Throttle (100мс – 300мс), когда вам нужно сэкономить ресурсы на «тяжелых» операциях, где микросекундная точность отображения не важна:

Отправка аналитики о перемещении пользователя на сервер.
Пересчет тяжелых сеток/раскладок при ресайзе окна.
Сохранение черновика положения элементов в LocalStorage.

### Почему степень экономии ресурсов отличается?

Для глубокого понимания оптимизации производительности (performance optimization) важно понимать, как именно `Throttle (100мс)` и `rAF (~16мс)` расходуют ресурсы:

#### 1. Количество обновлений состояния и рендеров React (Главный потребитель ресурсов)
Самая «дорогая» операция во фронтенде — это не сам JavaScript-код функций, а **изменение состояния React, сверка Virtual DOM (reconciliation) и последующая перерисовка реального DOM**.
* **Throttle (100мс):** Гарантирует максимум **10 обновлений состояния в секунду** (10 fps для логики). За 10 секунд активного движения мыши React перерисует компонент всего **~100 раз**.
* **rAF (~16мс):** Синхронизируется с частотой обновления экрана. На стандартном мониторе (60 Гц) это максимум **60 обновлений в секунду** (60 fps). На современных экранах **120 Гц / 144 Гц** rAF будет выполняться **120 или 144 раза в секунду**! За 10 секунд React перерисует компонент **600–1200+ раз**.
* **Вывод:** `Throttle` экономит ресурсы процессора (CPU) на рендеринг в **6–12 раз эффективнее**, чем rAF.

#### 2. Накладные расходы на выполнение самого JS-кода (CPU Overhead)
* В случае с **rAF** (в текущей реализации) при каждом из **573 сырых событий** браузер вынужден дергать Web API: вызывать обработчик, делать `cancelAnimationFrame` и планировать новый `requestAnimationFrame`. Это создает постоянную микронагрузку на Call Stack.
* В случае с **Throttle** обработчик при "лишних" событиях просто делает быструю проверку условий (например, проверка таймера/флага) и мгновенно завершается, не задействуя тяжелые Web API браузера.

#### 3. Энергоэффективность и GPU (Где rAF выигрывает)
Несмотря на то, что `rAF` заставляет процессор делать больше вычислений, у него есть уникальное преимущество перед `Throttle` с точки зрения **видеокарты (GPU) и батареи**:
* **Проблема Throttle:** Функция с таймером срабатывает асинхронно в случайные моменты времени, которые никак не связаны с циклом обновления экрана монитора (V-Sync). Это может приводить к тому, что изменения происходят сразу после перерисовки кадра, вызывая микродёргания экрана (Layout Thrashing / Jank).
* **Сила rAF:** Он выполняет код **ровно тогда, когда браузер собирается перерисовать экран**, предотвращая лишнюю работу GPU. Если вкладка браузера неактивна (свернута), браузер полностью **ставит rAF на паузу**, экономя 100% ресурсов батареи. `Throttle` (на базе `setTimeout`) продолжит выполняться в фоновом режиме.

#### Сводная таблица сравнения экономии ресурсов

| Критерий | Сырые события (Raw) | rAF (~16мс / 60-120fps) | Throttle (100мс / 10fps) |
| :--- | :--- | :--- | :--- |
| **Нагрузка на CPU (React рендеры)** | 🚨 **Экстремальная** (сотни раз в сек) | ⚠️ **Умеренная** (до 60-120 раз в сек) | 🟢 **Минимальная** (макс 10 раз в сек) |

Файл демонстрирует **4 реальных сценария применения throttle** в React:

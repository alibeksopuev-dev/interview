# `Record<string, T | undefined>` вместо индексной сигнатуры `[id: string]: T`

## Условие задачи

Дан нетипизированно-безопасный словарь:

```typescript
interface UserMap {
  [id: string]: User
}

function getName(map: UserMap, id: string) {
  // map[id] имеет тип User, даже если ключа нет —
  // .name упадёт в рантайме на undefined
  return map[id].name
}
```

Перепиши так, чтобы:
- обращение по несуществующему ключу было видно компилятору как потенциальный `undefined`;
- `getName` не падал в рантайме на несуществующем ключе, а возвращал `undefined`.

---

## Решение

```typescript
type UserMap = Record<string, User | undefined>

function getName(map: UserMap, id: string): string | undefined {
  const user = map[id]
  if (!user) return undefined // сужение убирает undefined
  return user.name
}

// или с optional chaining:
function getName2(map: UserMap, id: string) {
  return map[id]?.name
}
```

---

## Ключевые детали

### 1. Почему индексная сигнатура `[id: string]: User` врёт

Индексная сигнатура `{ [id: string]: User }` говорит компилятору: «для любого строкового ключа здесь лежит `User`». Это неправда — словарь почти никогда не содержит значения для всех возможных строк. TS верит сигнатуре буквально, поэтому `map[id]` типизируется как `User`, а не `User | undefined`, и `.name` проходит проверку типов — но падает в рантайме, если ключа нет.

### 2. `Record<string, User | undefined>` — честный тип

`Record<string, User | undefined>` говорит то же самое про множество ключей, но честно указывает, что значение может отсутствовать. Это вынуждает caller обработать `undefined` явно — либо через `if (!user) return`, либо через `?.`.

### 3. `noUncheckedIndexedAccess`

Флаг tsconfig `"noUncheckedIndexedAccess": true` делает шаг дальше: **любой** доступ по индексу (через `[key: string]: T` или `Record<string, T>`) автоматически даёт `T | undefined`, без необходимости явно писать `| undefined` в типе значения. Это самый надёжный способ — защита включается на уровне проекта, а не зависит от того, вспомнил ли автор типа дописать `| undefined`.

### 4. Сужение типа (`if (!user) return`) против `?.`

Оба способа корректно убирают `undefined`:
- `if (!user) return undefined` — явная ранняя проверка, удобна, если дальше нужно несколько обращений к `user`.
- `map[id]?.name` — компактнее для одного обращения, но если бы нужно было два поля (`user.name`, `user.email`), пришлось бы повторять `?.` или один раз сохранить в переменную.

### 5. Чем это отличается от `as User` или `!`

Можно было бы написать `map[id] as User` или `map[id]!.name`, чтобы заглушить ошибку компилятора — но это просто переносит проблему в рантайм без всякой защиты, ничем не отличаясь от исходного бага. Цель задачи — не убрать ошибку типов, а исключить сам класс рантайм-падений.

## Частые вопросы

### Если ключ гарантированно существует (например, только что добавили), нужен ли guard?

Технически в моменте — нет, но тип всё равно `User | undefined`, и TS будет требовать проверки при каждом обращении. Если уверенность в существовании ключа абсолютна и доказуема в этой же функции (например, только что сделали `map[id] = ...`), можно использовать локальную переменную, сохранённую до этого момента, а не повторно читать через индекс.

### `Map<string, User>` — не лучше ли просто использовать `Map`?

`Map.get(key)` в TS by default тоже возвращает `T`, а не `T | undefined`! Чтобы получить честный тип, нужен либо `noUncheckedIndexedAccess` (он не влияет на `Map.get`, увы), либо обёртка над `.get()`, либо просто помнить, что `.get()` может вернуть `undefined`, несмотря на тип. `Record` + `noUncheckedIndexedAccess` для словарей-объектов в этом смысле безопаснее «из коробки».

### А что насчёт массивов — `arr[i]`?

Та же проблема: `arr[i]` по умолчанию типизирован как `T`, даже если `i` вне диапазона. `noUncheckedIndexedAccess` исправляет это и для массивов — `arr[i]` становится `T | undefined`.

## Сложность алгоритма

- **Временная сложность**: $O(1)$ — обращение по ключу словаря.
- **Пространственная сложность**: $O(1)$.

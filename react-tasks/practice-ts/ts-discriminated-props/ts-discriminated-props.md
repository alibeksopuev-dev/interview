# Пропсы кнопки допускают невозможные комбинации

## Условие задачи

Дан тип пропсов кнопки:

```typescript
interface ButtonProps {
  label: string
  href?: string          // ссылка
  onClick?: () => void   // кнопка
  external?: boolean     // имеет смысл только для href
}
```

Оба поля `href` и `onClick` опциональны, поэтому компилятор разрешает:
- передать оба одновременно (непонятно, что должно произойти при клике на ссылку);
- не передать ни одного (кнопка без всякого поведения);
- передать `external` без `href` (бессмысленно).

Перепиши тип так, чтобы такие комбинации были ошибкой компиляции, а не багом в рантайме.

---

## Решение

```typescript
type ButtonProps =
  | { label: string; href: string; external?: boolean; onClick?: never }
  | { label: string; onClick: () => void; href?: never; external?: never }

function renderButton(props: ButtonProps) {
  if ('href' in props) {
    return {
      tag: 'a' as const,
      label: props.label,
      href: props.href,
      target: props.external ? '_blank' : undefined,
    }
  }
  return {
    tag: 'button' as const,
    label: props.label,
    onClick: props.onClick,
  }
}

// renderButton({ label: 'x' }) — ошибка: не подходит ни под один вариант ✅
// renderButton({ label: 'x', href: '/a', onClick: () => {} }) — ошибка ✅
```

## Ключевые детали

### 1. Discriminated union вместо одного widened-интерфейса

Вместо одного интерфейса с двумя опциональными полями описываем два непересекающихся варианта объекта и объединяем их через `|`. Каждый вариант сам по себе валиден и полон — компилятор не позволит собрать значение, которое не подходит ни под один из них.

### 2. `onClick?: never` и `href?: never` — явный запрет «чужого» поля

Просто опустить поле в другом варианте недостаточно — TypeScript по умолчанию допускает «лишние» свойства не во всех контекстах (excess property checking работает только для литералов объектов). Явно прописывая `onClick?: never` в «ссылочном» варианте, мы говорим: если это поле и присутствует, то его тип — `never`, то есть туда нельзя положить ничего, кроме `undefined`. Это окончательно запрещает указать `onClick` рядом с `href`.

### 3. `'href' in props` — сужение (narrowing) внутри функции

Внутри `renderButton` пропсы имеют тип union. Проверка `'href' in props` — это type guard, который TypeScript понимает: в `if`-ветке `props` сужается до варианта со `href`, в `else`-ветке — до варианта с `onClick`. Благодаря этому `props.href` и `props.onClick` доступны без приведений типа.

### 4. Чистая функция вместо JSX для проверки поведения

В тестах и плейграунде `renderButton` возвращает обычный объект-описание (`{ tag, label, href, target }` или `{ tag, label, onClick }`), а не JSX-элемент. Это позволяет проверять логику чистыми assert'ами без рендеринга в DOM — сам React-компонент `Button` строится на этой функции тривиально (просто маппит результат на `<a>`/`<button>`).

## Частые вопросы

### Почему нельзя просто сделать `href` и `onClick` обязательными, но с `undefined`?

Если оба поля обязательны (`href: string | undefined`), вызывающий код всё равно может передать оба значения сразу — TypeScript не запрещает указать оба `string`. Защититься от одновременного присутствия можно только через объединение взаимоисключающих форм (discriminated union), а не ослаблением отдельных полей.

### А если вариантов больше двух (ссылка, кнопка, submit-кнопка формы)?

Discriminated union масштабируется на любое число вариантов — просто добавляется третья ветка `| { label: string; type: 'submit'; ... }`. Главное — у каждой ветки своя уникальная комбинация обязательных полей (или явный литерал-дискриминант типа `kind: 'link' | 'button'`), чтобы `in`-проверка или проверка по дискриминанту однозначно сужала тип.

### Не проще ли проверять конфликт в рантайме (throw на оба поля)?

Рантайм-проверка ловит ошибку только когда код уже выполняется (и то, если разработчик не забыл вызвать эту проверку). Discriminated union ловит её на этапе компиляции/в IDE — раньше, дешевле и без шанса забыть проверку.

## Сложность алгоритма

- **Временная сложность**: $O(1)$ — обычное условное ветвление и построение объекта.
- **Пространственная сложность**: $O(1)$.

# Exhaustiveness-проверка switch по union через `never`

## Условие задачи

Дан union `Action` и редьюсер на `switch`:

```typescript
type Action =
  | { type: 'increment' }
  | { type: 'decrement' }
  | { type: 'reset' } // добавили позже — забыли обработать

function reducer(state: number, action: Action): number {
  switch (action.type) {
    case 'increment': return state + 1
    case 'decrement': return state - 1
    // 'reset' не обработан — TS не предупредил, баг молчит
    default: return state
  }
}
```

`reset` добавили в union, но забыли дописать `case` в `switch`. Компилятор не пожаловался: `default: return state` тихо «съел» новый вариант, и `reducer(5, { type: 'reset' })` вернёт `5` вместо `0`. Как сделать так, чтобы забытый кейс ловился на этапе компиляции, а не в продакшене?

---

## Решение

```typescript
type Action =
  | { type: 'increment' }
  | { type: 'decrement' }
  | { type: 'reset' }

function assertNever(x: never): never {
  throw new Error('Необработанный вариант: ' + JSON.stringify(x))
}

function reducer(state: number, action: Action): number {
  switch (action.type) {
    case 'increment': return state + 1
    case 'decrement': return state - 1
    case 'reset': return 0
    default:
      // если добавить новый Action и забыть case —
      // здесь будет ошибка компиляции ✅
      return assertNever(action)
  }
}
```

---

## Ключевые детали

### 1. Почему `default: return state` — это баг-магнит

`default` в `switch` синтаксически валиден всегда, независимо от того, остались ли необработанные варианты union. TypeScript не анализирует, насколько `switch` "покрывает" все ветки `Action`, если в `default` просто что-то `return`-ится. Любой новый вариант union молча попадает в `default` и обрабатывается как "ничего не делать" — баг проявится только в рантайме, когда кто-то реально вызовет `reducer` с этим вариантом.

### 2. `never` — тип "невозможного" значения

`never` — это тип, у которого нет ни одного допустимого значения. Если после серии `case`, сужающих `action.type`, в `default` остаётся переменная типа `never`, значит TypeScript считает, что **все** варианты union уже обработаны выше. Если же остался необработанный вариант, его тип в `default`-ветке — не `never`, а оставшийся литерал (например, `'reset'`), и присвоить/передать его в параметр типа `never` нельзя — компилятор выдаст ошибку.

### 3. `assertNever(x: never): never` — ловушка для забытых кейсов

```typescript
function assertNever(x: never): never {
  throw new Error('Необработанный вариант: ' + JSON.stringify(x))
}
```

Эта функция принимает только `never`. Когда в `default` вызывается `assertNever(action)`:
- если все варианты обработаны выше — `action` в этой точке имеет тип `never`, вызов компилируется;
- если кто-то добавил новый вариант в `Action` и не дописал `case` — `action` в `default` имеет тип нового варианта (не `never`), и `assertNever(action)` **не компилируется**. Ошибка указывает прямо на забытый кейс.

Возврат `never` у самой функции (через `throw`) также удобен: TypeScript понимает, что после вызова `assertNever` код недостижим, и не требует дополнительного `return`.

### 4. Чем это лучше рантайм-проверки

Можно было бы просто бросать `throw new Error(...)` в `default` без `never`-параметра — это поймает баг в рантайме (на проде или в тесте), но не на этапе сборки. Передача `action` именно в параметр типа `never` сдвигает проверку на компиляцию: ошибка появится в IDE и в `tsc`, до того как код попадёт в продакшен.

## Частые вопросы

### А что если в `switch` используется не `action.type`, а сам `action`?

Идея та же: важно, чтобы TypeScript успел сузить тип до `never` к моменту `default`, перебрав дискриминант (`type`) во всех `case`. Сам `switch` может быть и по `action`, если у каждого `case` есть literal-сопоставление, но удобнее и нагляднее переключаться по полю-дискриминанту.

### Нужно ли реально бросать `Error` внутри `assertNever`?

Да, это и страховка на рантайм (если кто-то обошёл проверку типов — например, данные пришли по сети без валидации), и способ дать функции тип возврата `never` через `throw`. Без `throw` пришлось бы возвращать какое-то фиктивное значение, что менее честно.

### Работает ли это вне `switch`, например в цепочке `if/else if`?

Да — паттерн `assertNever` одинаково применим в конце цепочки `if/else if` по дискриминанту: в последнем `else` (или после всех `if`) значение должно сузиться до `never`, и его можно передать в `assertNever`.

## Сложность алгоритма

- **Временная сложность**: $O(1)$ — обычный `switch` с константным числом веток.
- **Пространственная сложность**: $O(1)$.

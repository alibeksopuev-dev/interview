# Защита от мутации пропсов через `readonly`

## Условие задачи

Дана нетипизированная (точнее — слабо типизированная) функция:

```typescript
function getSortedList(items: number[]): number[] {
  return items.sort((a, b) => a - b)
}
```

`Array.prototype.sort` сортирует массив **на месте** и возвращает ссылку на тот же массив. Если `items` пришёл извне (например, из пропсов компонента или из состояния родителя), эта функция тихо мутирует данные, которыми может пользоваться кто-то ещё.

Перепиши функцию так, чтобы:
- тип параметра запрещал мутирующие методы (`.sort`, `.push`, `.splice`, ...) на этапе компиляции;
- функция возвращала новый отсортированный массив, не трогая исходный.

---

## Решение

```typescript
function getSortedList(items: readonly number[]): number[] {
  // items.sort(...) — ошибка компиляции, readonly запрещает мутацию
  return [...items].sort((a, b) => a - b)
  // альтернатива (ES2023): return items.toSorted((a, b) => a - b)
}

const original = [3, 1, 2]
const sorted = getSortedList(original)
console.log(sorted)   // [1, 2, 3]
console.log(original) // [3, 1, 2] — не изменился ✅
```

---

## Ключевые детали

### 1. `readonly T[]` — мутирующие методы пропадают из типа

`readonly number[]` (эквивалент `ReadonlyArray<number>`) убирает из типа все методы, изменяющие массив на месте: `sort`, `push`, `pop`, `splice`, `shift`, `unshift`, прямое присваивание по индексу (`items[0] = 1`). Остаются только неизменяющие операции: `map`, `filter`, `slice`, индексный доступ на чтение, `length` и т.п.

### 2. Копия перед мутацией — `[...items]`

Чтобы всё-таки отсортировать данные, нужен **новый** массив. Спред-оператор `[...items]` создаёт поверхностную копию — её можно мутировать сколько угодно, не трогая оригинал.

### 3. Неизменяющие методы ES2023 — `toSorted`, `toReversed`, `toSpliced`, `with`

Начиная с ES2023, у массивов появились неизменяющие аналоги мутирующих методов: `items.toSorted(cmp)` возвращает новый отсортированный массив, не трогая `items`, и при этом отлично работает прямо на `readonly T[]` — копировать вручную не нужно.

### 4. `readonly` — это компиляционная защита, не рантайм-заморозка

`readonly number[]` не делает массив иммутабельным в рантайме (в отличие от `Object.freeze`). Это чисто типовая аннотация: TypeScript запретит вызвать мутирующий метод **через эту переменную/параметр**, но если у того же массива есть другая ссылка с типом `number[]`, через неё мутация всё ещё возможна. Защита работает только в той части кода, где тип объявлен как `readonly`.

## Частые вопросы

### Чем `readonly T[]` отличается от `Readonly<T[]>`?

Это одно и то же — `Readonly<T[]>` разворачивается в `readonly T[]`. Но для объектов `Readonly<T>` делает только поверхностный (shallow) readonly: вложенные объекты/массивы остаются мутируемыми.

### Почему не `Object.freeze`?

`Object.freeze` — рантайм-механизм: попытка мутации не бросает ошибку в нестрогом режиме (просто молча игнорируется) либо бросает `TypeError` в strict mode, но в любом случае это проверяется в момент выполнения, а не на этапе сборки. `readonly` в типах ловит проблему раньше — при компиляции/в IDE, до запуска кода.

### А если нужна глубокая иммутабельность объекта с вложенными полями?

Встроенного глубокого `Readonly` нет — `Readonly<T>` поверхностный. Нужен рекурсивный mapped type (`DeepReadonly<T>`) или библиотека (`type-fest`'s `ReadonlyDeep`).

## Сложность алгоритма

- **Временная сложность**: $O(n \log n)$ — стандартная сортировка массива из `n` элементов.
- **Пространственная сложность**: $O(n)$ — на копию массива перед сортировкой.

# Разбор useQueryAdvanced — Кэширование, Дедупликация, Retry, Ревалидация

---

## Почему базового `useQuery` недостаточно?

Базовый `useQuery` решает одну задачу: безопасно управлять промисом в `useEffect`. Но в реальных
приложениях возникают четыре дополнительные проблемы:

| Проблема | Симптом | Решение |
| :--- | :--- | :--- |
| Повторные запросы одних данных | Каждый переход на страницу — новый HTTP-запрос | **Кэширование** |
| Несколько компонентов запрашивают одно | N компонентов = N одинаковых запросов | **Дедупликация** |
| Нестабильный сервер | Один сбой — пользователь видит ошибку | **Retry** |
| Устаревшие данные | Данные актуальны только в момент загрузки | **Ревалидация** |

Именно эти четыре механизма и реализует библиотека React Query / SWR под капотом.

## Модуль 1: Кэширование (`useQueryCached`)

### Идея

Хранить ответы в глобальном `Map` за пределами React. Если ключ уже есть — отдать мгновенно,
HTTP-запрос не делать.

```ts
// Глобальный — живёт всё время работы приложения (не сбрасывается при ремаунте)
const cache = new Map<string, unknown>()
```

### Почему `Map` глобальный, а не `useState` / `useRef`?

- `useState` — локален для экземпляра компонента. При ремаунте (смена страницы → возврат) — данные потеряны.
- `useRef` — то же самое, привязан к lifetime компонента.
- Глобальная переменная вне React — живёт пока вкладка открыта. Компонент A и компонент B видят один и тот же кэш.

### Ключ кэша

```ts
useQueryCached<RMCharacter>(
  'character-1',        // ← ключ: любая уникальная строка, обычно URL
  () => fetch('/api/character/1').then(r => r.json()),
  [id],
)
```

**Ключ = контракт.** Одинаковый ключ → одни данные. Разный ключ → разные данные.

### Алгоритм

```
useEffect срабатывает:
  ↓
cache.has(key)?
  ДА  → setState({ status: 'success', data: cache.get(key) })  — мгновенно, без fetch
  НЕТ → setState({ status: 'loading' })
         → fn() → fetch
         → cache.set(key, data)         — сохраняем для следующих обращений
         → setState({ status: 'success', data })
```

### Инвалидация кэша

```ts
clearCache('character-1')  // удалить конкретный ключ
clearCache()               // очистить всё
```

Без инвалидации кэш — вечный. В реальных приложениях добавляют TTL (time-to-live):

```ts
cache.set(key, { data, expiresAt: Date.now() + 60_000 })
// При чтении: if (Date.now() > entry.expiresAt) → удалить, перезапросить
```

### Флаг `fromCache`

Хук возвращает `fromCache: boolean` — позволяет UI показать индикатор «данные из кэша».
Это полезно для отладки и для UX (пользователь понимает, что данные могут быть не свежими).

### Big O

| Операция | Сложность |
| --- | --- |
| Чтение из кэша (`Map.get`) | **O(1)** |
| Запись в кэш (`Map.set`) | **O(1)** |
| Очистка одного ключа (`Map.delete`) | **O(1)** |
| Полная очистка (`Map.clear`) | **O(n)** — n = размер кэша |

## Модуль 2: Дедупликация запросов (`useQueryDeduped`)

### Проблема

```tsx
// Страница монтирует два независимых компонента:
<UserCard userId={1} />   // → fetch('/api/user/1')
<UserStats userId={1} />  // → fetch('/api/user/1')  ← дубль!
```

Два компонента делают один и тот же запрос одновременно. В сети уходят два идентичных HTTP-запроса.

### Идея: Map промисов

```ts
// Глобальный реестр «запросов в полёте»
const inFlight = new Map<string, Promise<unknown>>()
```

Первый компонент, который запрашивает ключ `"user-1"`, создаёт промис и регистрирует его.
Второй — находит промис по ключу и подписывается на него вместо создания нового.

### Алгоритм

```
Компонент A вызывает useQueryDeduped('user-1', fn):
  inFlight.has('user-1') === false
  → promise = fn()
  → inFlight.set('user-1', promise)
  → deduped = false

Компонент B вызывает useQueryDeduped('user-1', fn) в тот же тик:
  inFlight.has('user-1') === true
  → promise = inFlight.get('user-1')   ← тот же самый промис!
  → deduped = true                      ← HTTP-запрос не создавался

Промис завершается:
  → inFlight.delete('user-1')           ← очищаем реестр
  → оба компонента получают данные из одного .then()
```

### Почему это работает?

Промис в JavaScript — объект. Его можно передать в несколько `.then()`, и все колбэки получат
одно значение. Два компонента буквально слушают один и тот же HTTP-запрос.

### Чем отличается от кэширования?

| | Кэш | Дедупликация |
| --- | --- | --- |
| **Когда работает** | Повторные запросы (позже) | Одновременные запросы (сейчас) |
| **Что хранит** | Результат (данные) | Промис (в процессе) |
| **После завершения** | Данные остаются | Запись удаляется |

### Big O

| Операция | Сложность |
| --- | --- |
| Поиск промиса (`Map.has` + `Map.get`) | **O(1)** |
| Регистрация промиса (`Map.set`) | **O(1)** |
| Очистка после завершения (`Map.delete`) | **O(1)** |

## Модуль 3: Повтор при ошибке (`useQueryRetry`)

### Проблема

Сетевые ошибки бывают временными: сервер перегружен, DNS-сбой, пакет потерялся. Показывать
пользователю ошибку после первой неудачи — плохой UX.

### Экспоненциальная задержка (Exponential Backoff)

```
Попытка 1 → провал → ждём 1000мс  (2⁰ × 1000)
Попытка 2 → провал → ждём 2000мс  (2¹ × 1000)
Попытка 3 → провал → ждём 4000мс  (2² × 1000)
Попытка 4 → провал → ошибка финальная
```

Формула задержки: `delay = 1000 * 2^attempt`

**Зачем экспонента, а не фиксированная задержка?**
Если сервер упал — множество клиентов начнут стучать одновременно. Фиксированная задержка
создаёт «шторм запросов» каждые N секунд. Экспонента + случайный jitter (дрожание) распределяют
нагрузку во времени.

### Архитектура: `useRef` для таймера

```ts
const retryTimerRef = useRef<ReturnType<typeof setTimeout> | null>(null)
```

Таймер retry хранится в `useRef`, а не в локальной переменной, потому что cleanup эффекта должен
его отменить. Если deps изменятся во время ожидания — cleanup вызывается, `clearTimeout` отменяет
запланированный retry.

### Алгоритм

```
fn() → ошибка
  currentAttempt < maxRetries?
    ДА  → delay = 1000 * 2^currentAttempt
          currentAttempt++
          setAttempt(currentAttempt)   ← UI показывает "Попытка 2/4"
          setTimeout(run, delay)
    НЕТ → setState({ status: 'error', error })  ← все попытки исчерпаны
```

### Cleanup при смене deps

```ts
return () => {
  ignore = true
  if (retryTimerRef.current) clearTimeout(retryTimerRef.current)  // отмена запланированного retry
}
```

Если deps изменятся пока идёт ожидание между попытками — таймер отменяется, старый retry не случится.

### Big O

| Операция | Сложность |
| --- | --- |
| Каждая попытка | **O(1)** |
| Всего попыток | **O(maxRetries)** — константа, не зависит от данных |
| Суммарное время ожидания | **O(2^maxRetries)** — экспоненциально, но maxRetries обычно 3–5 |

## Модуль 4: Фоновая ревалидация (SWR)

### Паттерн stale-while-revalidate

Название пришло из HTTP-заголовков (`Cache-Control: stale-while-revalidate`). Смысл:

> Отдай пользователю то, что есть сейчас (пусть немного устаревшее), и параллельно тихо обнови.

Альтернатива — сбрасывать в `loading` при каждом обновлении. Это вызывает «мигание» интерфейса
(контент исчезает → скелетон → контент появляется).

### Два `useEffect`: зачем?

```ts
// Эффект 1: первоначальная загрузка — показываем loading
useEffect(() => {
  setState({ status: 'loading' })
  fn().then(data => setState({ status: 'success', data }))
}, deps)

// Эффект 2: фоновый интервал — НЕ сбрасываем в loading
useEffect(() => {
  const id = setInterval(() => {
    setRevalidating(true)          // ← только флаг, данные остаются на экране
    fn().then(data => {
      setState({ status: 'success', data })
      setRevalidating(false)
    })
  }, revalidateMs)
  return () => clearInterval(id)
}, [...deps, revalidateMs])
```

Разделение на два эффекта гарантирует: фоновый интервал никогда не вызывает `setState({ status: 'loading' })`.

### Ручная ревалидация: трюк с `tick`

```ts
const [tick, setTick] = useState(0)

// В deps добавляем tick — его изменение перезапускает эффект
useEffect(() => { fn()... }, [...deps, tick])

// Кнопка "Обновить"
const revalidate = useCallback(() => setTick(t => t + 1), [])
```

`tick` — счётчик, который не несёт смысловой нагрузки. Его единственная цель — стать триггером
для `useEffect`. Каждый `setTick` → deps изменились → эффект перезапускается → новый запрос.

### Флаг `isFirstRun` через `useRef`

```ts
const isFirstRun = useRef(true)

useEffect(() => {
  if (isFirstRun.current) {
    isFirstRun.current = false
    setState({ status: 'loading' })  // первый раз — полная загрузка
  } else {
    setRevalidating(true)            // повторный — только флаг
  }
  ...
}, [...deps, tick])
```

`useRef` здесь оправдан: нам нужно значение, которое сохраняется между рендерами, но его изменение
**не должно вызывать рендер**. `useState` вызвал бы лишний рендер.

### При ошибке ревалидации

```ts
fn().catch(() => {
  setRevalidating(false)
  // Старые данные остаются — ошибку фона не показываем
})
```

Ошибка фонового обновления не ломает UI. Пользователь видит чуть устаревшие данные — это лучше,
чем внезапный экран ошибки.

### Big O

| Операция | Сложность |
| --- | --- |
| Первая загрузка | **O(1)** |
| Каждая ревалидация | **O(1)** |
| Память (хранит только последние данные) | **O(1)** |

## Сравнение всех четырёх хуков

| | `useQueryCached` | `useQueryDeduped` | `useQueryRetry` | `useQuerySWR` |
| :--- | :--- | :--- | :--- | :--- |
| **Что решает** | Повторные запросы | Одновременные дубли | Нестабильный сервер | Устаревшие данные |
| **Хранилище** | `Map<key, data>` | `Map<key, Promise>` | `useRef` таймер | `setInterval` |
| **Loading при повторе** | Нет (мгновенно) | Нет (один промис) | Да (новый запрос) | Нет (тихо) |
| **Когда очищается** | Вручную / TTL | После завершения промиса | После maxRetries | Никогда (интервал) |
| **Аналог в React Query** | `staleTime` | Встроено по умолчанию | `retry` опция | `refetchInterval` |

---

## Как они сочетаются вместе

В реальной библиотеке (React Query, SWR) все четыре механизма работают одновременно:

```
Запрос приходит
  ↓
Есть в кэше и не устарел? → отдать мгновенно + фоновая ревалидация
  ↓
Нет → уже летит такой запрос? → подписаться на него (дедупликация)
  ↓
Нет → fetch()
  ↓
Ошибка? → retry с backoff
  ↓
Успех → записать в кэш → отдать UI
  ↓
Через N секунд → тихая ревалидация (SWR)
```

Именно это делает `queryClient` под капотом каждого `useQuery` из `@tanstack/react-query`.

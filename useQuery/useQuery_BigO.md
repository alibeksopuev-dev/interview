# Разбор хука useQuery и Big O

---

## Что такое useQuery?

**useQuery** — хук React, который управляет жизненным циклом асинхронного запроса (промиса) и предоставляет компоненту его актуальное состояние через дискриминированный union.

Хук принимает функцию `fn`, возвращающую промис, и массив зависимостей `deps`. Каждый раз, когда `deps` меняются, предыдущий запрос «забывается» и запускается новый.

**Аналогия из жизни:** официант в ресторане. Вы сделали заказ (запрос #1), потом передумали и изменили заказ (запрос #2). Кухня всё ещё готовит блюдо #1, но официант знает — подать нужно только блюдо #2. Блюдо #1 придёт, но официант его проигнорирует.

---

## Ключевые концепции

| Концепция                   | Роль в useQuery                                                                          |
| --------------------------- | ---------------------------------------------------------------------------------------- |
| **Дискриминированный union** | `status` однозначно определяет, какие поля доступны: `data` или `error`                 |
| **`useEffect` + `deps`**    | Перезапускает запрос при изменении зависимостей, очищает предыдущий через `cleanup`     |
| **`ignore` флаг**           | Предотвращает запись устаревших ответов после смены `deps` или размонтирования           |
| **`setState({ status: 'loading' })`** | Сброс состояния в начале каждого нового запроса — не показываем старые данные |
| **Замыкание `fn`**          | `fn` захватывает актуальные `deps` снаружи — хук не хранит их отдельно                 |

## TypeScript-типизация

### Дискриминированный union (Discriminated Union)

```ts
type AsyncState<T> =
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; error: Error }
```

Это не просто объект с опциональными полями, а **три взаимоисключающих состояния**. TypeScript'у достаточно проверить `status`, чтобы сузить тип:

```ts
if (request.status === 'loading') {
  // тип здесь: { status: 'loading' }
  // request.data — ❌ не существует в этом типе
}
if (request.status === 'success') {
  // тип здесь: { status: 'success'; data: T }
  // request.data — ✅ доступно
}
if (request.status === 'error') {
  // тип здесь: { status: 'error'; error: Error }
  // request.error.message — ✅ доступно
}
```

**Почему не `{ data?: T; error?: Error; loading: boolean }`?**

Такой подход порождает недопустимые комбинации: `loading: true` и `data: someValue` одновременно — логически невозможная ситуация. Дискриминированный union делает невалидные состояния **нереализуемыми на уровне типов**.

---

### Generic `<T>`

```ts
export default function useQuery<T>(
  fn: () => Promise<T>,
  deps: DependencyList = [],
): AsyncState<T>
```

`T` выводится из возвращаемого типа `fn`. Если `fn` возвращает `Promise<Character[]>`, то `state.data` автоматически будет типизирован как `Character[]` — без явного указания.

---

### `DependencyList`

```ts
import { DependencyList } from 'react'
// type DependencyList = ReadonlyArray<unknown>
```

Это официальный тип React для массива зависимостей `useEffect`. Использование `unknown[]` или `any[]` было бы менее точно.

## Механизм `ignore` флага — защита от Race Condition

### Зачем нужен `ignore` — просто о главном

Представь: ты открыл страницу профиля пользователя №1. Запрос пошёл на сервер. Пока он летит — ты быстро перешёл на профиль №2. Теперь летят **два запроса одновременно**.

Сервер отвечает непредсказуемо — иногда первый запрос приходит **позже** второго. Тогда экран покажет данные пользователя №1, хотя ты уже смотришь на №2.

`ignore` — это флажок «мне больше не нужен этот ответ». Когда ты перешёл на №2, старый запрос помечается: `ignore = true`. Ответ приходит, видит флажок — и молча выбрасывается в мусор.

```
Ты на профиле №1 → запрос A уходит
Ты переходишь на №2 → запрос A помечается: ignore = true
                     → запрос B уходит
Ответ A приходит → видит ignore = true → выброшен ✅
Ответ B приходит → ignore = false → данные записаны ✅
```

Без этого флажка — экран врёт. С ним — всегда показываются данные последнего актуального запроса.

---

### Что такое Race Condition?

**Race Condition** («состояние гонки») — баг, когда результат программы зависит от того, **в каком порядке завершатся** два асинхронных события, а порядок этот непредсказуем.

В `useQuery` это выглядит так: два HTTP-запроса «гонятся» к финишу, и побеждает не тот, что должен — более старый запрос приходит последним и перезаписывает актуальные данные.

### Что такое `deps = "re"`?

В трассировках ниже запись `deps = "re"` — это сокращение: **массив зависимостей `[query]` в данный момент содержит значение `"re"`**.

Реальный код, который моделируется:

```tsx
function SearchPage() {
  const [query, setQuery] = useState('')

  const results = useQuery(
    () => fetch(`/api/search?q=${query}`).then(r => r.json()),
    [query], // ← deps
  )
  // ...
}
```

Когда пользователь печатает слово «react» по букве:

```
нажал "r"  → query = "r"  → deps = ["r"]  → useEffect перезапускается → запрос #1
нажал "e"  → query = "re" → deps = ["re"] → useEffect перезапускается → запрос #2
нажал "a"  → query = "rea"→ deps = ["rea"]→ useEffect перезапускается → запрос #3
...
```

### Проблема: без защиты

```
deps = "r"   → запрос #1 начат (медленный сервер — 500мс)
deps = "re"  → запрос #2 начат (попал в кэш   — 100мс)

t=100мс: запрос #2 завершился → setState({ status: 'success', data: [...] })
t=500мс: запрос #1 завершился → setState({ status: 'success', data: [...] })
                                  ☠️ Перезаписал данные! Показаны результаты для "r", не "re"
```

Пользователь ввёл `"re"`, видит результаты для `"r"` — это и есть Race Condition.

### Решение: локальный `ignore` флаг

```ts
useEffect(() => {
  let ignore = false         // ← создаётся при каждом запуске эффекта

  setState({ status: 'loading' })

  fn().then((data) => {
    if (ignore) return       // ← если deps изменились, этот эффект уже "умер"
    setState({ status: 'success', data })
  })

  return () => {
    ignore = true            // ← cleanup: помечаем этот запуск устаревшим
  }
}, deps)
```

**Почему `ignore` живёт в `useEffect`, а не в `useRef`?**

Каждый запуск `useEffect` создаёт **собственное замыкание** со своим `ignore`. Это ключевое отличие:

- `useRef` — одно значение на весь lifetime компонента. Если поставить `ignore` в ref, запрос #1 и запрос #2 будут делить один флаг.
- Локальная переменная внутри `useEffect` — своя копия для каждого запуска. Cleanup запуска #1 ставит `ignore = true` только для запуска #1, не затрагивая запуск #2.

### Пошаговая трассировка Race Condition (с защитой через `ignore`)

```
deps = "r"   (t=0)
  → Эффект A запускается
  → ignoreA = false
  → setState({ status: 'loading' })
  → начат fetch для "r"

deps = "re"  (t=50мс)
  → React вызывает cleanup эффекта A: ignoreA = true  ← "r" запрос помечен устаревшим
  → Эффект B запускается
  → ignoreB = false
  → setState({ status: 'loading' })
  → начат fetch для "re"

t=150мс → fetch "re" завершился
  → ignoreB === false → setState({ status: 'success', data: resultsForRe })  ✅

t=600мс → fetch "r" завершился
  → ignoreA === true → return (ранний выход)  ✅ данные "r" проигнорированы
```

## Пошаговая трассировка: нормальный сценарий

```ts
const character = useQuery(
  () => fetch(`/api/character/${id}`).then(r => r.json()),
  [id]
)
```

```
Шаг 1: id = 1, компонент монтируется
  → useEffect запускается
  → setState({ status: 'loading' })       → рендер: <p>Loading...</p>
  → fetch('/api/character/1') начат

Шаг 2: ~200мс — fetch завершился успешно
  → ignore === false
  → setState({ status: 'success', data: { name: 'Rick', ... } })
  → рендер: <p>Data: Rick Sanchez</p>

Шаг 3: пользователь нажал "следующий" → id = 2
  → cleanup: ignore = true (запрос #1 помечен устаревшим)
  → useEffect перезапускается
  → setState({ status: 'loading' })       → рендер: <p>Loading...</p>
  → fetch('/api/character/2') начат

Шаг 4: fetch завершился успешно
  → ignore === false
  → setState({ status: 'success', data: { name: 'Morty', ... } })
  → рендер: <p>Data: Morty Smith</p>
```

## Трассировка: ошибка сети

```
Шаг 1: id = 999 (несуществующий)
  → setState({ status: 'loading' })
  → fetch('/api/character/999') начат

Шаг 2: сервер вернул 404 → fetch выбросил Error
  → .catch((error) => { ... })
  → ignore === false
  → setState({ status: 'error', error: new Error('Not Found') })
  → рендер: <p>Error: Not Found</p>
```

## Разбор кода с комментариями

```ts
export default function useQuery<T>(
  fn: () => Promise<T>,      // функция, которая делает запрос — замыкает актуальные deps
  deps: DependencyList = [], // изменение deps = новый запрос
): AsyncState<T> {

  // Начальное состояние — loading (ещё ничего не пришло)
  const [state, setState] = useState<AsyncState<T>>({ status: 'loading' })

  useEffect(() => {
    let ignore = false // локальный флаг: жив ли этот конкретный запуск эффекта?

    setState({ status: 'loading' }) // сбрасываем стейт при каждом новом запросе

    fn()
      .then((data) => {
        if (ignore) return // deps изменились или компонент размонтирован — выходим
        setState({ status: 'success', data })
      })
      .catch((error) => {
        if (ignore) return // то же самое для ошибок
        setState({ status: 'error', error })
      })

    return () => {
      ignore = true // cleanup: помечаем этот запуск "мёртвым" перед следующим
    }
  }, deps) // React отслеживает изменения deps и перезапускает эффект

  return state // всегда возвращаем актуальное состояние
}
```

## Типичные ошибки

| Ошибка | Что сломается |
| :--- | :--- |
| **Не сбрасывать в `loading` при смене deps** | Пока новый запрос идёт, отображаются старые данные |
| **Использовать `useRef` вместо локальной переменной** | Один флаг на все запросы — Race Condition вернётся |
| **Не вызывать `setState` в `.catch`** | Ошибки не отображаются, UI завис в `loading` вечно |
| **Передавать `fn` в `deps`** | Если `fn` создаётся inline — бесконечный цикл запросов |
| **Не проверять `ignore` в `.catch`** | Ошибка устаревшего запроса перезапишет успешный результат |

---

### Подробный разбор частых ошибок

#### 1. Передавать `fn` в массив зависимостей

```ts
// ❌ Бесконечный цикл
useQuery(
  () => fetch(`/api/character/${id}`).then(r => r.json()),
  [id, fn] // fn — новая функция при каждом рендере
)

// ✅ Правильно — fn ссылается на id через замыкание
useQuery(
  () => fetch(`/api/character/${id}`).then(r => r.json()),
  [id]
)
```

Функция `fn` создаётся заново при каждом рендере компонента. Если добавить её в `deps`, эффект будет перезапускаться на каждый рендер, вызывая ещё один рендер — бесконечный цикл.

**Решение:** `fn` не нужна в `deps`, потому что она уже захватывает актуальные значения через замыкание. В `deps` нужны только те значения, от которых зависит *результат запроса*.

---

#### 2. `useRef` вместо локальной переменной для `ignore`

```ts
// ❌ Неправильно — один ref на все запуски
const ignoreRef = useRef(false)

useEffect(() => {
  ignoreRef.current = false
  fn().then(data => {
    if (ignoreRef.current) return // ← сломано: запрос #2 тоже поставит current=true
    setState(...)
  })
  return () => { ignoreRef.current = true }
}, deps)
```

Когда deps меняются и запускаются запросы #1 и #2 одновременно:
- cleanup #1 ставит `ignoreRef.current = true`
- эффект #2 сразу ставит `ignoreRef.current = false`
- cleanup #2 (при следующей смене deps) ставит `ignoreRef.current = true`
- запрос #1 завершается и видит `ignoreRef.current = true` — ок
- но запрос #2 тоже может увидеть `ignoreRef.current = true` если deps сменились снова — данные потеряны

Локальная переменная — изолированное замыкание для каждого запуска, это единственно правильный подход.

## useQuery и Event Loop

```
Компонент рендерится (id=1)
       ↓
useEffect планируется (Microtask queue после paint)
       ↓
React запускает useEffect
       ↓ (синхронно)
setState({ status: 'loading' }) → рендер
fn() вызван → fetch() → Web API (HTTP запрос в фоне)
ignore = false
       ↓ (асинхронно, через Macrotask queue)
HTTP ответ получен → Promise.resolve → Microtask queue
       ↓
.then(data => { if (ignore) return; setState({status:'success', data}) })
       ↓
setState → рендер компонента с данными
```

## Big O

### Временная сложность: `O(1)` на сам хук

| Операция                  | Сложность  |
| ------------------------- | ---------- |
| `useState` инициализация  | `O(1)`     |
| `useEffect` регистрация   | `O(1)`     |
| `setState` вызов          | `O(1)`     |
| Проверка `ignore`         | `O(1)`     |
| **Итого (без запроса)**   | **`O(1)`** |

Сетевой запрос `fn()` — вне зоны ответственности хука. Его сложность определяет реализация `fn`.

### Пространственная сложность: `O(1)`

- `state` — одна переменная (дискриминированный union)
- `ignore` — один булев флаг на запуск эффекта

## Что useQuery НЕ делает (намеренно)

Этот вопрос про **безопасное управление асинхронным состоянием в эффекте**, а не про полноценную библиотеку:

| Возможность           | useQuery | React Query / SWR |
| --------------------- | -------- | ----------------- |
| Кэширование           | ❌        | ✅                 |
| Дедупликация запросов | ❌        | ✅                 |
| Повтор при ошибке     | ❌        | ✅                 |
| Фоновая ревалидация   | ❌        | ✅                 |
| Race Condition защита | ✅        | ✅                 |
| TypeScript generics   | ✅        | ✅                 |

## Сравнение подходов управления async-состоянием

| Подход | Плюсы | Минусы |
| :--- | :--- | :--- |
| **useQuery (данная реализация)** | Прост, без зависимостей, учебный эталон | Нет кэша, нет retry |
| **useReducer + useEffect** | Явные переходы состояний | Больше кода |
| **React Query / SWR** | Полный feature-set | Внешняя зависимость |
| **useState + useEffect вручную** | Максимальный контроль | Легко допустить Race Condition |

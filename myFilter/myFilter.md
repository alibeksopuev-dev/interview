# Реализация `Array.prototype.myFilter`

## Условие задачи

Реализовать метод `myFilter` на прототипе `Array`, который ведёт себя идентично нативному `Array.prototype.filter`:
- Проходит по всем элементам исходного массива, пропуская пустые ячейки (holes) в разреженных массивах.
- Вызывает функцию-колбэк (предикат) для каждого существующего элемента, передавая туда текущее значение, индекс и сам исходный массив.
- Поддерживает необязательный аргумент `thisArg` для привязки контекста `this` внутри колбэка.
- Возвращает **новый плотный** массив, содержащий только те элементы исходного массива, для которых колбэк вернул истинное (truthy) значение.
- Не изменяет исходный массив.

---

## Реализация

```typescript
export {};

declare global {
  interface Array<T> {
    // 1. Сигнатура для Type Guard (сужение типов)
    myFilter<S extends T>(
      callbackFn: (value: T, index: number, array: Array<T>) => value is S,
      thisArg?: any,
    ): Array<S>;

    // 2. Стандартная сигнатура для обычных предикатов
    myFilter(
      callbackFn: (value: T, index: number, array: Array<T>) => unknown,
      thisArg?: any,
    ): Array<T>;
  }
}

Array.prototype.myFilter = function <T>(
  this: T[],
  callbackFn: (value: T, index: number, array: T[]) => unknown,
  thisArg?: any,
): any[] {
  const arrayLength = this.length;
  const array: T[] = [];

  for (let index = 0; index < arrayLength; index++) {
    if (
      Object.hasOwn(this, index) &&
      callbackFn.call(thisArg, this[index], index, this)
    ) {
      array.push(this[index]);
    }
  }

  return array;
};
```

## Ключевые детали

### 1. `[]` и `array.push` для построения результата

В отличие от `myMap`, где результирующий массив должен сохранять исходную длину и пустые ячейки (holes), `myFilter` возвращает плотный массив, содержащий только отфильтрованные элементы.
Поэтому мы инициализируем обычный пустой массив `const array = []` и наполняем его с помощью стандартного метода `array.push(...)`:
```typescript
array.push(this[index]);
```
Это гарантирует, что в результирующем массиве не будет никаких дыр, а его длина будет точно равна числу элементов, для которых предикат вернул истинное значение.

### 2. Проверка `Object.hasOwn(this, index)` — пропуск дыр

Нативный метод `filter` посещает только те индексы массива, у которых есть присвоенные значения (включая `undefined`, если оно было присвоено явно). Пустые ячейки (пропуски/holes) игнорируются:

```typescript
const sparse = [1, , 3];
// Индекс 1 пропущен, колбэк для него вызываться не будет
sparse.myFilter(x => x !== undefined); // [1, 3]
```

Использование `Object.hasOwn(this, index)` гарантирует, что мы не будем вызывать колбэк для несуществующих индексов разреженного массива.

### 3. Значение предиката приводится к true/false неявно или явно в условии `if`

В нашей реализации условие проверки выглядит так:
```typescript
if (
  Object.hasOwn(this, index) &&
  callbackFn.call(thisArg, this[index], index, this)
)
```
Поскольку результат `callbackFn.call` используется непосредственно в условии `if`, JavaScript автоматически приводит возвращаемое значение колбэка к логическому типу (Boolean). Это полностью соответствует поведению встроенного `filter`.

---

### 4. В чем разница между `this` и `thisArg`?

*   **`this` (контекст вызова метода `myFilter`)**
    *   Указывает на массив, на котором был вызван метод.
    *   В типизации `this: T[]` — это псевдопараметр TypeScript, сообщающий компилятору тип контекста.
*   **`thisArg` (контекст для вызова колбэка)**
    *   Необязательный второй параметр метода `myFilter`.
    *   Задает значение `this` при вызове функции `callbackFn`.
    *   Позволяет использовать внешние объекты внутри обычных функций-колбэков (для стрелочных функций контекст не меняется из-за лексического связывания).

Пример:
```typescript
const filterer = {
  minLimit: 10,
  isAboveLimit(value: number) {
    return value > this.minLimit; // this ссылается на filterer благодаря передаче thisArg
  }
};

const numbers = [5, 12, 8, 20];
const result = numbers.myFilter(filterer.isAboveLimit, filterer); // [12, 20]
```

---

### 5. Три параметра `callbackFn` и их назначение

Предикат вызывается со следующими параметрами: `callbackFn(value, index, array)`

1.  **`value`** — текущий элемент массива (`this[index]`).
2.  **`index`** — числовой индекс текущего элемента (`index`).
3.  **`array`** — ссылка на оригинальный массив, по которому осуществляется проход (`this`).

---

### 6. Зачем нужен `callbackFn.call`

Для вызова колбэка с передачей кастомного контекста `thisArg` используется метод `.call()`:
```typescript
callbackFn.call(thisArg, this[index], index, this);
```
Метод `.call` первым параметром принимает объект, который станет контекстом `this` внутри вызываемой функции, а последующие параметры передаются как аргументы функции.

### 7. Подробный разбор типизации

```typescript
export {}; // Делает файл модулем для изоляции типов

declare global {
  interface Array<T> {
    // 1. Сигнатура для Type Guard (сужение типов)
    myFilter<S extends T>(
      callbackFn: (value: T, index: number, array: Array<T>) => value is S,
      thisArg?: any,
    ): Array<S>;

    // 2. Стандартная сигнатура для обычных предикатов
    myFilter(
      callbackFn: (value: T, index: number, array: Array<T>) => unknown,
      thisArg?: any,
    ): Array<T>;
  }
}
```

*   **`interface Array<T>`** — расширяет стандартный глобальный интерфейс массива с помощью Declaration Merging.
*   **Две перегрузки метода (`overloads`)**:
    *   **Перегрузка с Type Guard (`myFilter<S extends T>`)** — принимает колбэк вида `value is S` и позволяет TypeScript автоматически сужать тип результирующего массива до `Array<S>`. Например, при фильтрации `(string | undefined)[]` предикатом `(x): x is string => ...` результат будет `string[]`.
    *   **Стандартная перегрузка** — принимает колбэк, возвращающий `unknown`/`boolean`, и возвращает `Array<T>`.
*   **`thisArg?: any`** — опциональный аргумент для проброса контекста.
*   **`Array<S> / Array<T>`** — возвращаемые типы в зависимости от перегрузки.

#### Зачем писать `S extends T`?

`S extends T` — это ограничение (constraint) на generic-параметр: оно гарантирует, что `S` может быть только подтипом (или тем же типом), что и `T`, а не вообще любым произвольным типом.

**1. Смысловая корректность.** `myFilter` не может породить в результате значения, которых не было в исходном массиве — он только отбирает существующие элементы. Значит, результирующий тип `S` физически обязан быть подмножеством `T`. Без `extends T` ничто не мешало бы написать Type Guard вида `(x): x is SomeOtherType => true`, и TypeScript вывел бы `Array<SomeOtherType>` — что абсурдно, ведь `filter` никогда не превращает `string` в другой, никак не связанный тип.

**2. Без constraint типобезопасность ломается.** Если убрать `extends T`:
```typescript
myFilter<S>(callbackFn: (value: T, ...) => value is S, ...): Array<S>;
```
компилятор не сможет проверить, что `S` вообще имеет отношение к `T`, и будет доверять любой аннотации `value is S`, даже нелогичной.

**3. Как это работает на примере.** Для `(string | undefined)[]` и колбэка `(x): x is string => ...`:
*   `T` = `string | undefined`
*   TS проверяет: `string extends (string | undefined)` — выполняется
*   Значит `S = string` — валидная подстановка, и результат `Array<S>` = `string[]`

Если бы кто-то попытался написать guard `(x): x is number => ...` для того же массива, TS выдал бы ошибку компиляции, потому что `number` не `extends (string | undefined)` — и это ожидаемое поведение: нельзя «отфильтровать» из `(string | undefined)[]` то, что даже не является `string` или `undefined`.

Тот же паттерн использует нативный `lib.es5.d.ts` для `Array.prototype.filter`.

#### Что такое перегрузка (overloads) и нормально ли иметь две сигнатуры?

**Перегрузка функций (Function Overloading)** — это возможность описать несколько способов вызова одной и той же функции с разными типами аргументов и результатов, используя при этом единую реализацию на уровне JavaScript.

В TypeScript перегрузка состоит из двух частей:
1. **Сигнатуры вызова (Overload Signatures)** — это публичные интерфейсы функции, которые видит внешний код (их может быть сколько угодно).
2. **Сигнатура реализации (Implementation Signature)** — сама функция с телом, которая должна быть совместима со всеми сигнатурами вызова. Внешний код её не видит.

Для `filter` иметь две сигнатуры — это **стандартная практика**, заимствованная из встроенной библиотеки TypeScript (`lib.es5.d.ts`), потому что метод решает две разные задачи типизации:
1. **Фильтрация без изменения типа элементов**: `[1, 2, 3]` -> оставляем только четные. Тип элементов не меняется (`number[]` -> `number[]`).
2. **Фильтрация с сужением типа (Type Narrowing)**: `[1, undefined, 2]` -> отсеиваем `undefined`. Здесь тип массива должен измениться с `(number | undefined)[]` на `number[]`. Для этого TypeScript должен понять, что колбэк является «защитником типа» (Type Guard).

Без перегрузки нам пришлось бы либо жертвовать сужением типов (и разработчикам приходилось бы вручную приводить тип через `as number[]`), либо заставлять всех писать Type Guard, даже если они просто проверяют четность чисел.

#### Что такое сужение типа (Type Narrowing)?

**Сужение типа (Type Narrowing)** — это процесс, при котором TypeScript анализирует структуру кода и уменьшает (делает более конкретным) диапазон возможных типов для переменной в определенной ветке выполнения.

Например, если у нас есть тип `string | undefined`, сужение типа позволяет превратить его в чистую строку `string` после проверки:
```typescript
function process(val: string | undefined) {
  if (val !== undefined) {
    // Внутри этого блока тип val сузился до string
    console.log(val.toUpperCase()); 
  }
}
```

##### Причем здесь `myFilter` и User-Defined Type Guards?

Когда мы фильтруем массив смешанных типов `(string | undefined)[]`, обычная проверка `val !== undefined` внутри `myFilter` не дает TypeScript понять, что результирующий массив больше не содержит `undefined`:
```typescript
const arr: (string | undefined)[] = ['apple', undefined, 'banana'];
const res = arr.myFilter(x => x !== undefined); 
// Без первой сигнатуры тип res всё еще (string | undefined)[]
```

Чтобы TypeScript узнал о сужении внутри массива, мы используем **пользовательский защитник типа (User-Defined Type Guard)** с оператором `is` в возвращаемом типе колбэка:
```typescript
const isNotUndefined = (x: string | undefined): x is string => x !== undefined;

const res = arr.myFilter(isNotUndefined);
// Благодаря сигнатуре <S extends T>(...) => value is S
// тип res теперь строго string[]
```

##### Почему тип не сужается без Type Guard: `unknown` vs `value is S`

Без первой перегрузки TypeScript видит только вторую сигнатуру:
```typescript
myFilter(callbackFn: (value: T, index: number, array: Array<T>) => unknown, thisArg?: any): Array<T>;
```
Она говорит: «колбэк возвращает что-то (`unknown`), а результат — всё тот же `Array<T>`». TypeScript **не анализирует тело** колбэка `x => x !== undefined` и не понимает, что после такой проверки в массиве не остаётся `undefined`. Он видит только тип возвращаемого значения (булево) — и тип массива на выходе не меняется. Поэтому `res` в примере выше остаётся `(string | undefined)[]`, хотя вы точно знаете, что `undefined` там уже нет.

Первая перегрузка решает это иначе — она требует не любой колбэк, а именно **Type Guard**:
```typescript
myFilter<S extends T>(
  callbackFn: (value: T, index: number, array: Array<T>) => value is S,
  thisArg?: any,
): Array<S>;
```
Ключевое отличие — возвращаемый тип колбэка `value is S`, а не `boolean`/`unknown`. Это специальный синтаксис TS: функция не просто возвращает true/false, а **утверждает компилятору**: «если я вернула true — value имеет тип S». Компилятор верит этой аннотации на слово (сама реализация колбэка не проверяется рантаймом — это чисто подсказка типов на этапе компиляции).

Поэтому когда колбэк написан с явной аннотацией:
```typescript
const isNotUndefined = (x: string | undefined): x is string => x !== undefined;
const res = arr.myFilter(isNotUndefined);
```
TypeScript видит сигнатуру `x is string`, подставляет `S = string` (так как `string extends (string | undefined)`), и по перегрузке №1 выводит тип результата как `Array<S>` = `string[]`. Вот и всё «сужение» — тип массива буквально стал уже (`string | undefined` → `string`) на основании явного утверждения в колбэке, а не анализа его тела.

Если же колбэк написан без аннотации `x is string` (обычный `x => x !== undefined`), TS откатится ко второй перегрузке, и `res` останется `(string | undefined)[]`. В рантайме обе версии работают одинаково — разница исключительно в типизации.

## Пошаговое выполнение `[1, 2, , 4].myFilter(x => x % 2 === 0)`

| Шаг | `index` | Есть элемент? (`Object.hasOwn`) | Результат предиката | Действие | Состояние `array` |
|:---:|:-------:|:------------------------------:|:-------------------:|:--------:|:-----------------:|
| 1 | 0 | `true` (значение: `1`) | `false` | Пропущен | `[]` |
| 2 | 1 | `true` (значение: `2`) | `true` | Добавлен | `[2]` |
| 3 | 2 | `false` (дыра) | Не вызывается | Пропущен | `[2]` |
| 4 | 3 | `true` (значение: `4`) | `true` | Добавлен | `[2, 4]` |

Результат: `[2, 4]`

## Частые вопросы

### Зачем длина массива сохраняется в `arrayLength` до цикла?

По спецификации длина массива фиксируется перед первым вызовом колбэка. Если колбэк в процессе работы начнет добавлять новые элементы в исходный массив, они не будут посещены, так как цикл остановится на исходном значении `arrayLength`.

### Почему используется `Object.hasOwn` вместо `index in this`?

Оператор `in` проверяет наличие свойства не только у самого объекта, но и во всей его цепочке прототипов. Если кто-то добавит свойство с числовым ключом в `Array.prototype` (например, `Array.prototype[1] = 'test'`), то `in` вернет `true` для пустой ячейки разреженного массива под индексом `1`. `Object.hasOwn` проверяет исключительно собственные свойства объекта, гарантируя корректное поведение.

## Сложность алгоритма

- **Временная сложность**: $O(n)$ — один проход по массиву длины $n$.
- **Пространственная сложность**: $O(n)$ — в худшем случае (когда все элементы подходят под условие) создается новый массив той же длины.

# Разбор алгоритма selectData и Big O

---

## Что такое selectData?

**selectData** — функция фильтрации и агрегации набора тренировочных сессий.

Принимает массив сессий и объект опций. Возвращает новый массив сессий, не мутируя входные данные.

**Аналогия из жизни:** Запрос к базе данных с `WHERE`, `GROUP BY` и `ORDER BY` одновременно — но реализованный вручную на JavaScript, без SQL-движка.

---

## Структура данных

```ts
type Session = {
  user: number       // ID пользователя
  duration: number   // продолжительность в минутах
  equipment: Array<string>  // отсортированный массив, только 5 видов
}

type Options = {
  user?: number          // фильтр по конкретному пользователю
  minDuration?: number   // минимальная продолжительность (включительно)
  equipment?: Array<string>  // хотя бы один из перечисленных типов
  merge?: boolean        // объединить сессии одного пользователя
}
```

---

## Ключевые концепции

| Концепция | Роль в selectData |
| --- | --- |
| **`Array.slice().reverse()`** | Клонирует и переворачивает массив без мутации оригинала |
| **`Map<userId, session>`** | Отслеживает уже встреченного пользователя за `O(1)` |
| **`Set<string>` для equipment** | `O(1)` проверка наличия и `O(1)` добавление при дедупликации |
| **`setHasOverlap`** | Пересечение двух Set за `O(min(|A|, |B|))` вместо `O(n*m)` |
| **Double reverse trick** | Сохраняет правило «объединенный объект занимает место **последнего** вхождения» |

---

## Алгоритм в двух фазах

### Фаза 1 — Построение рабочего списка (с учётом `merge`)

```
sessions → .slice().reverse()
              ↓
     для каждой сессии (в reversed-порядке):
         merge ON + пользователь уже встречался?
           → обновить существующий клон (duration += ..., equipment.add(...))
         иначе:
           → клонировать сессию (equipment: new Set(...))
           → если merge ON, записать в Map<userId, клон>
           → добавить в sessionsProcessed
              ↓
     sessionsProcessed.reverse()   ← восстанавливаем порядок
```

### Фаза 2 — Фильтрация

```
для каждой сессии в sessionsProcessed:
    user != null → проверяем session.user
    equipment.size > 0 → setHasOverlap(...)
    minDuration != null → session.duration >= minDuration
    все условия выполнены → конвертируем Set → sorted Array → results.push
```

## Double Reverse Trick — подробный разбор

Задача: при `merge: true` объединенный объект должен **занять место последнего вхождения** пользователя в оригинальном массиве.

### ❓ Зачем нам знать, является ли сессия последней для пользователя?

Это необходимо для строгого соблюдения бизнес-требований и сохранения правильного хронологического порядка активности пользователей:

1. **Сохранение хронологии последних действий:** В реальных задачах последняя сессия представляет собой самое актуальное состояние или время активности. Размещение объединенного объекта на месте последнего вхождения сохраняет временной порядок наиболее свежих тренировок пользователей относительно друг друга.
2. **Разница в итоговом порядке (Пример):**
   Представим исходный массив сессий:
   ```js
   [A1, B1, A2, B2, A3] // цифра — номер тренировки пользователя A или B
   ```
   * *Если группировать по первому появлению:* `A` (индекс 0) окажется перед `B` (индекс 1). Результат: `[A_merged, B_merged]`.
   * *Если группировать по последнему появлению (как требует ТЗ):* Последнее вхождение `B` находится на индексе 3 (`B2`), а `A` — на индексе 4 (`A3`). Результат: `[B_merged, A_merged]`.
   
   Порядок уникальных пользователей в результате кардинально меняется.
3. **Управление добавлением в результирующий массив:**
   Чтобы сформировать итоговый массив за один проход ($O(n)$), мы должны добавить (`push`) новый объект в результирующий список **ровно один раз** — именно в тот момент, когда обрабатывается **последняя** сессия пользователя. Все остальные (более ранние) сессии должны лишь обновлять его данные (`duration` и `equipment`), не создавая новых записей.

---

### ❌ В чём сложность при обычном обходе (слева направо)?

При прямом обходе (слева направо), когда мы встречаем `A1` на индексе 0, мы **не знаем**, появятся ли сессии пользователя A дальше в массиве. Чтобы узнать, является ли текущее вхождение последним, нам пришлось бы каждый раз выполнять дорогостоящее сканирование всего оставшегося массива до конца (`lookahead`). Это увеличило бы временную сложность алгоритма до неэффективной квадратичной $O(n^2)$.

---

### 🔄 Как это решает двойной разворот (Double Reverse)

Разворачивая массив, мы превращаем задачу поиска **последнего** вхождения в простую задачу поиска **первого** вхождения.

#### Шаг 1: Первый разворот (`sessions.slice().reverse()`)
* **Исходный массив:** `[A1, B1, A2, B2, A3]`
* **После разворота:** `[A3, B2, A2, B1, A1]`

Теперь первое появление пользователя в перевернутом массиве гарантированно является его последним вхождением в оригинальном массиве:
* **Первое появление A:** `A3` (реально последнее в оригинале).
* **Первое появление B:** `B2` (реально последнее в оригинале).

#### Шаг 2: Обход перевернутого массива
Мы идем по массиву `[A3, B2, A2, B1, A1]` слева направо:
* **Встречаем `A3`** (пользователь A встречен впервые):
  * Клонируем `A3`.
  * Записываем в результирующий массив: `sessionsProcessed = [A_merged]`.
* **Встречаем `B2`** (пользователь B встречен впервые):
  * Клонируем `B2`.
  * Добавляем в результирующий массив: `sessionsProcessed = [A_merged, B_merged]`.
* **Встречаем `A2`** (пользователь A уже встречался):
  * Прибавляем параметры к `A_merged` (через ссылку в `Map`), новую запись в `sessionsProcessed` не добавляем.
* **Встречаем `B1`** (пользователь B уже встречался):
  * Прибавляем параметры к `B_merged`.
* **Встречаем `A1`** (пользователь A уже встречался):
  * Прибавляем параметры к `A_merged`.

В конце Шага 2 получаем:
```js
sessionsProcessed = [A_merged, B_merged]
```

#### Шаг 3: Второй разворот (`sessionsProcessed.reverse()`)
Поскольку мы обходили массив с конца, порядок уникальных пользователей получился перевернутым (`A` перед `B`).

Разворачиваем массив обратно:
```js
sessionsProcessed = [B_merged, A_merged]
```

Порядок полностью восстановился. Объединенный объект `B_merged` занял позицию своего последнего оригинального вхождения (`B2`), а `A_merged` — своего (`A3`).

#### Пошаговая визуализация на примере:

```
Оригинал (индексы 0..6):
  i=0  user=8
  i=1  user=7   ← первое вхождение user 7
  i=2  user=1
  i=3  user=7   ← второе вхождение user 7
  i=4  user=7   ← ПОСЛЕДНЕЕ вхождение user 7 — здесь должен быть объединенный объект
  i=5  user=2
  i=6  user=2
```

**Шаг 1 — reverse:**
```
  i=0  user=2   ← бывший i=6
  i=1  user=2   ← бывший i=5
  i=2  user=7   ← бывший i=4  (теперь ПЕРВОЕ вхождение user 7 в reversed-виде)
  i=3  user=7
  i=4  user=7
  i=5  user=1
  i=6  user=8
```

**Шаг 2 — обход reversed массива:**
- `user=2` (i=0): первый раз → клонируем, добавляем в sessionsProcessed[0], Map[2]=клон
- `user=2` (i=1): Map[2] есть → обновляем клон (duration+= , equipment.add)
- `user=7` (i=2): первый раз → клонируем, добавляем в sessionsProcessed[1], Map[7]=клон
- `user=7` (i=3): Map[7] есть → обновляем клон
- `user=7` (i=4): Map[7] есть → обновляем клон
- `user=1` (i=5): первый раз → клонируем, sessionsProcessed[2]
- `user=8` (i=6): первый раз → клонируем, sessionsProcessed[3]

**sessionsProcessed перед финальным reverse:** `[user2, user7, user1, user8]`

**Шаг 3 — reverse обратно:** `[user8, user7, user1, user2]`

Итог: `user7` стоит на месте бывшего `i=4` (последнее вхождение в оригинале). ✅

### Можно ли здесь обойтись только `Map.values()`, как в `mergeData`?

**Логически и математически — да**, при условии, что `merge` всегда равен `true`. 

Если бы мы рассматривали сценарий только с обязательным объединением, то вызов `Array.from(sessionsForUser.values()).reverse()` также идеально восстановил бы порядок последних вхождений:
1. **Реверс:** Последнее вхождение в оригинале становится первым в реверсированном массиве.
2. **Вставка в Map:** Порядок первой вставки в `Map` будет соответствовать порядку этих встреченных элементов (последних в оригинале, но перевернутых).
3. **Финальный `.reverse()`:** Переворачивая `Map.values()`, мы полностью восстановили бы исходный порядок.

#### Почему же тогда используется массив `sessionsProcessed`?

Использование промежуточного массива `sessionsProcessed` вместо `Map.values()` решает две важные задачи проектирования:

1. **Поддержка режима без объединения (`merge: false`):**
   Если объединение выключено, нам нужно сохранить абсолютно все сессии (включая повторяющиеся тренировки одного пользователя). `Map` хранит только уникальные ключи (`userId`), поэтому при использовании только `Map` мы бы потеряли дубликаты. Массив `sessionsProcessed` гарантирует сохранность всех записей.
2. **Единый конвейер (pipeline) фильтрации:**
   Благодаря тому, что сборка данных (в первой фазе) всегда складывает результат в `sessionsProcessed` (будь то уникальные объединенные объекты при `merge: true` или полная копия при `merge: false`), **Фаза 2 (фильтрация)** работает абсолютно одинаково и переиспользует один и тот же лаконичный код фильтрации для обоих режимов.

## TypeScript-типизация

### Generics и вспомогательная функция `setHasOverlap`

```ts
function setHasOverlap<T>(setA: Set<T>, setB: Set<T>): boolean {
  for (const val of Array.from(setA)) {
    if (setB.has(val)) return true
  }
  return false
}
```

#### Зачем нужна эта функция?

Она решает задачу **эффективного поиска пересечений множеств (Set intersection)** для фильтрации по оборудованию (`options.equipment`).

1. **Оптимизация производительности (Big O):**
   * **Обычный подход с массивами:** Если бы мы хранили оборудование как `Array` и использовали `session.equipment.some(eq => options.equipment.includes(eq))`, то на каждую проверку уходило бы `O(e1 * e2)` операций (поскольку метод `.includes` выполняет линейный поиск по массиву). Для всего списка сессий это дало бы квадратичную сложность `O(n * e)`.
   * **Оптимальный подход с Set:** Превратив массив запрашиваемого оборудования в `Set` один раз перед циклом, мы получаем `O(1)` доступ к его элементам. Функция `setHasOverlap` проверяет наличие элементов через `setB.has(val)`, что занимает `O(1)`. Сложность проверки падает до **`O(min(|setA|, |setB|))`**, что для небольших множеств работает практически мгновенно.
2. **Ранний выход (Short-circuiting):**
   Функция возвращает `true` сразу же, как только находит первое общее оборудование, прекращая дальнейший обход элементов.
3. **Почему дженерик `<T>`?**
   * Дженерик делает функцию универсальной: она одинаково хорошо работает с `Set<string>`, `Set<number>` или пользовательскими типами.
   * Строгая типизация через `Set<T>` гарантирует, что TypeScript не позволит сравнить несовместимые множества (например, `Set<string>` и `Set<number>`), что предотвращает логические ошибки при разработке.

### Внутреннее представление vs публичный контракт

В коде используются разные структуры данных для внутренней обработки и для возвращаемого результата. Это решает две ключевые архитектурные задачи.

#### 1. Зачем разделять `sessionsForUser` (Map) и `sessionsProcessed` (Array)?

Они выполняют принципиально разные роли:
* **`sessionsForUser` (Map):** Служит исключительно для **быстрого поиска за $O(1)$** по ID пользователя при слиянии сессий (`options.merge: true`). Если бы мы искали уже обработанного пользователя в обычном массиве, сложность поиска на каждом шаге составляла бы линейные $O(n)$, превращая обход массива в неэффективный квадратичный $O(n^2)$.
* **`sessionsProcessed` (Array):** Служит для сохранения **исходного хронологического порядка** и всех элементов. Хотя в JavaScript `Map` гарантирует обход элементов в порядке их вставки (insertion order), при выключенном объединении (`merge: false`) нам необходимо сохранить все сессии каждого пользователя без дедупликации. `Map` не справится с этой задачей, так как он может хранить только уникальные ключи (`userId`) и перезаписал бы предыдущие сессии одного и того же пользователя. Использование массива позволяет иметь единый конвейер данных для обоих режимов (`merge: true` и `merge: false`).

#### Почему «первое вхождение в перевернутом = последнее в оригинале»?

На конкретном примере массива `SESSIONS`:

**Исходный порядок:**
```ts
const SESSIONS = [
  { user: 8, duration: 50,  equipment: ['bench'] },                  // index 0
  { user: 7, duration: 150, equipment: ['dumbbell', 'kettlebell'] }, // index 1
  { user: 1, duration: 10,  equipment: ['barbell'] },                // index 2
  { user: 7, duration: 100, equipment: ['bike', 'kettlebell'] },     // index 3
  { user: 7, duration: 200, equipment: ['bike'] },                   // index 4  ← ПОСЛЕДНЕЕ вхождение user 7
  { user: 2, duration: 200, equipment: ['treadmill'] },              // index 5
  { user: 2, duration: 200, equipment: ['bike'] },                   // index 6  ← ПОСЛЕДНЕЕ вхождение user 2
]
```

**После разворота (`reversedSessions`):**
```ts
[
  { user: 2, ...['bike'] },                   // index 0 (бывший 6) ← ПЕРВОЕ появление user 2 в цикле
  { user: 2, ...['treadmill'] },              // index 1 (бывший 5)
  { user: 7, ...['bike'] },                   // index 2 (бывший 4) ← ПЕРВОЕ появление user 7 в цикле
  { user: 7, ...['bike', 'kettlebell'] },     // index 3 (бывший 3)
  { user: 1, ...['barbell'] },                // index 4 (бывший 2) ← ПЕРВОЕ появление user 1 в цикле
  { user: 7, ...['dumbbell', 'kettlebell'] }, // index 5 (бывший 1)
  { user: 8, ...['bench'] },                  // index 6 (бывший 0) ← ПЕРВОЕ появление user 8 в цикле
]
```

**Как это используется при слиянии (`merge: true`):**

| i | user | `sessionsForUser.has(user)` | Действие |
|---|------|-----------------------------|----------|
| 0 | 2 | ❌ нет | Это **первое** появление `user 2` в цикле (= **последняя** его сессия в оригинале). Клонируем объект, записываем в `Map` и `sessionsProcessed`. |
| 1 | 2 | ✅ есть | Более ранняя сессия. Суммируем данные к уже созданному клону по ссылке из `Map`. В `sessionsProcessed` не добавляем. |
| 2 | 7 | ❌ нет | **Первое** появление `user 7` в цикле (= **последняя** сессия в оригинале, `index 4`). Клонируем, регистрируем в `Map` и `sessionsProcessed`. |
| 3 | 7 | ✅ есть | Более ранняя сессия. Суммируем данные к клону из `Map`. |
| 4 | 1 | ❌ нет | **Первое** появление `user 1`. Клонируем, добавляем. |
| 5 | 7 | ✅ есть | Более ранняя сессия. Суммируем данные к клону из `Map`. |
| 6 | 8 | ❌ нет | **Первое** появление `user 8`. Клонируем, добавляем. |

Итого `sessionsProcessed` перед финальным разворотом: `[user2, user7, user1, user8]`. После `.reverse()` → `[user8, user1, user7, user2]`, что точно соответствует позициям последних вхождений в оригинальном массиве.

### ❓ Детальный разбор механики слияния (Вопросы с собеседований)

#### Вопрос 1: Что значит «Суммируем данные к уже созданному клону по ссылке из `Map`. В `sessionsProcessed` не добавляем»? Где это в коде?
Это реализовано в ветке `if` внутри цикла `forEach` по развернутому массиву сессий ([selectData.ts L37-L42](file:///Users/alibek/WebstormProjects/interview/selectData/selectData.ts#L37-L42)):
```ts
if (options?.merge && sessionsForUser.has(session.user)) {
  // Пользователь уже встречался — обновляем существующий объединенный объект
  const userSession = sessionsForUser.get(session.user)!
  userSession.duration += session.duration
  session.equipment.forEach(e => userSession.equipment.add(e))
}
```

**Как это работает "на пальцах":**
1. В JavaScript/TypeScript объекты передаются **по ссылке**.
2. Когда мы впервые встретили пользователя (например, `ID 7`), мы создали объект-клон `clonedSession`, добавили ссылку на него в `Map` (`sessionsForUser.set(7, clonedSession)`) и запушили в массив `sessionsProcessed`.
3. Когда мы встречаем сессию пользователя `7` во второй раз (а так как массив развернут, то хронологически эта сессия **более ранняя**):
   * Условие `sessionsForUser.has(7)` возвращает `true`.
   * Мы извлекаем из `Map` ссылку: `const userSession = sessionsForUser.get(7)`. Это **тот же самый** физический объект в памяти, который уже лежит в массиве `sessionsProcessed`.
   * Мы меняем его свойства прямо "на месте": увеличиваем `duration` и добавляем новые элементы в `Set`.
   * Поскольку это ссылка, изменения **автоматически отражаются внутри массива `sessionsProcessed`**.
   * Мы **не вызываем** `sessionsProcessed.push()`, благодаря чему у пользователя `7` в итоговом массиве не плодятся дубликаты сессий, а остается ровно одна запись.

#### Вопрос 2: Склеивает ли метод `sessionsForUser.set(session.user, clonedSession)` (строка 50 в selectData.ts) то, что было, с `clonedSession`?
**Нет, не склеивает.** 

Метод `Map.prototype.set(key, value)` является стандартной операцией ассоциации ключа со значением. Он либо записывает новое значение, либо полностью перезаписывает старое. 

Однако в ветке `else` (где находится этот вызов) **нечего перезаписывать и не с чем склеивать**:
* Мы заходим в ветку `else` только в том случае, если `sessionsForUser.has(session.user)` вернул `false` — то есть **этого пользователя мы еще ни разу не встречали** в нашем цикле.
* Поэтому `sessionsForUser.set(session.user, clonedSession)` просто **регистрирует** созданную сессию-клон в `Map` для данного пользователя.
* Это необходимо исключительно для того, чтобы при обработке **следующих** (более ранних) сессий этого же пользователя сработал блок `if` (описанный в Вопросе 1), и мы смогли получить ссылку на этот клон и "склеить" новые данные с ним.

#### 2. Зачем использовать `Set` внутри, но отдавать `Array` наружу? (Type-boundary pattern)

```ts
// Внутренний рабочий тип (equipment как Set — для O(1) операций)
const sessionsProcessed: Array<{
  user: number
  duration: number
  equipment: Set<string>   // ← Set
}> = []

// Публичный тип возврата (equipment как Array — как в оригинале)
type Session = { user: number; duration: number; equipment: Array<string> }  // ← Array
```

* **Внутри (`Set`):** Используется для максимальной производительности во время слияния и фильтрации. Благодаря `Set` дедупликация оборудования (метод `.add()`) и проверка пересечения фильтров (`setHasOverlap`) работают за константное время $O(1)$.
* **Снаружи (`Array`):** Используется для соблюдения публичного контракта. Клиентский код ожидает стандартный массив строк `Array<string>` на выходе и не должен знать о деталях внутренней оптимизации алгоритма.

Конвертация происходит только на выходе из функции:
```ts
equipment: Array.from(session.equipment).sort()
```

Это **type-boundary pattern**: внутри алгоритма оптимальное представление, снаружи — публичный контракт.

### Опциональные опции и `?? null` guard

```ts
options?.user != null && options.user !== session.user
```

- `?.user` — optional chaining: если `options` не передан, возвращает `undefined`, не выбрасывает ошибку.
- `!= null` — проверяет одновременно `null` и `undefined` (loose equality), не исключает `0`.
  - Важно: если написать `!options?.user`, то `user: 0` ошибочно засчитается как «не задан».

### Дедупликация оборудования с помощью Set при слиянии

При объединении сессий нам нужно собрать все уникальные типы оборудования, которые использовал пользователь. Это реализовано с помощью строки:
```ts
session.equipment.forEach(e => userSession.equipment.add(e))
```

#### Как это работает по шагам:

1. **Разница в типах данных:**
   * `session.equipment` — это обычный массив `Array<string>` из текущей обрабатываемой сессии (например, `['bike', 'kettlebell']`).
   * `userSession.equipment` — это коллекция `Set<string>` в уже созданном объединенном объекте.

2. **Свойство уникальности Set:**
   Метод `Set.prototype.add(value)` автоматически проверяет, есть ли уже добавляемое значение в коллекции:
   * Если элемент уникален, он добавляется в `Set`.
   * Если такой элемент уже существует, операция просто игнорируется.
   * **Преимущество:** Нам не нужно писать ручные проверки через `.includes()`, что делает код лаконичным и быстрым ($O(1)$ для каждого элемента).

3. **Обновление по ссылке (In-place Mutation):**
   * Переменная `userSession` хранит **ссылку** на объект, который ранее был добавлен в массив `sessionsProcessed`.
   * Когда мы вызываем метод `.add(e)` на `userSession.equipment`, мы изменяем `Set` непосредственно внутри этого объекта в массиве `sessionsProcessed`.
   * Это абсолютно безопасно, так как при первой встрече пользователя объект был полностью склонирован (`new Set(session.equipment)`). Мы не мутируем исходный входящий массив `sessions`.

## Разбор кода с комментариями

```ts
export default function selectData(sessions: Array<Session>, options?: Options): Array<Session> {
  // ┌─ ФАЗА 1: клонируем и переворачиваем, не мутируя оригинал
  const reversedSessions = sessions.slice().reverse()

  // Map для O(1) поиска уже встреченного пользователя при merge
  const sessionsForUser = new Map<number, { user: number; duration: number; equipment: Set<string> }>()

  const sessionsProcessed: Array<{ user: number; duration: number; equipment: Set<string> }> = []

  reversedSessions.forEach(session => {
    if (options?.merge && sessionsForUser.has(session.user)) {
      // Пользователь уже есть — обновляем мёрдженный объект
      const userSession = sessionsForUser.get(session.user)!
      userSession.duration += session.duration
      session.equipment.forEach(e => userSession.equipment.add(e))  // Set автоматически дедуплицирует
    } else {
      const clonedSession = {
        ...session,
        equipment: new Set(session.equipment),  // new Set = клон, не мутируем оригинал
      }

      if (options?.merge) {
        sessionsForUser.set(session.user, clonedSession)  // регистрируем первое вхождение
      }

      sessionsProcessed.push(clonedSession)
    }
  })

  sessionsProcessed.reverse()  // восстанавливаем порядок после reversed-обхода
  // └─ конец ФАЗЫ 1

  // ┌─ ФАЗА 2: фильтрация
  // Создаём Set один раз до цикла — O(k) вместо пересоздания O(k) на каждую сессию
  const optionEquipments = new Set(options?.equipment)
  const results: Array<Session> = []

  sessionsProcessed.forEach(session => {
    if (
      (options?.user != null && options.user !== session.user) ||      // фильтр по юзеру
      (optionEquipments.size > 0 && !setHasOverlap(optionEquipments, session.equipment)) ||  // фильтр по оборудованию
      (options?.minDuration != null && options.minDuration > session.duration)  // фильтр по длительности
    ) {
      return  // short-circuit: пропускаем сессию при первом же несовпадении
    }

    results.push({
      ...session,
      equipment: Array.from(session.equipment).sort(),  // Set → отсортированный Array
    })
  })

  return results
  // └─ конец ФАЗЫ 2
}
```

## Big O

### n = количество сессий, k = количество типов equipment в опции

### Временная сложность

| Фаза | Операция | Сложность |
| --- | --- | --- |
| Реверс входного массива | `slice().reverse()` | `O(n)` |
| Обход reversed массива | forEach × n | `O(n)` |
| `Map.has` / `Map.get` / `Map.set` | на каждую сессию | `O(1)` |
| `Set.add` при мёрдже equipment | до 5 элементов | `O(1)` |
| Финальный reverse | `sessionsProcessed.reverse()` | `O(n)` |
| Создание `optionEquipments` Set | из k элементов | `O(k)` |
| Фильтрация | forEach × n | `O(n)` |
| `setHasOverlap` | min(k, 5) итераций | `O(1)` (т.к. max 5 типов) |
| `Array.from(set).sort()` | 5 элементов | `O(1)` |
| **Итого** | | **`O(n)`** |

### Пространственная сложность

| Структура | Размер |
| --- | --- |
| `reversedSessions` | `O(n)` — клон входного массива |
| `sessionsForUser` Map | `O(u)` — u уникальных пользователей, u ≤ n |
| `sessionsProcessed` | `O(n)` без мержа, `O(u)` с мержем |
| `results` | `O(n)` в худшем случае |
| **Итого** | **`O(n)`** |

## Типичные ошибки

| Ошибка | Что сломается |
| --- | --- |
| **Мутировать `session.equipment` напрямую** | Входные данные изменятся, последующие вызовы дадут неправильный результат |
| **Не делать reverse перед обходом** | Объединенный объект окажется на месте первого, а не последнего вхождения |
| **Использовать `includes()` вместо `Set`** | `O(n*m)` вместо `O(n)` для equipment-фильтра |
| **Проверять `!options?.equipment` вместо `size > 0`** | Пустой массив `[]` ошибочно активирует фильтр |
| **Проверять `!options?.user` вместо `!= null`** | `user: 0` засчитается как «не задан» |
| **Не клонировать equipment при push в results** | Set мутируется позже — результаты изменятся непредсказуемо |
| **Использовать `.reverse()` без `.slice()`** | Мутирует оригинальный массив сессий (поменяет порядок исходных данных) |

## Подробный разбор типичных ошибок

### 1. Мутация входных данных

```ts
// ❌ Неправильно: мутируем equipment оригинальной сессии

### 2. Неправильная проверка `user: 0`

```

---

### 3. Фильтр по пустому equipment

```ts
// ❌ Неправильно: пустой массив [] фильтрует всё
const optionEquipments = new Set(options?.equipment)
if (!setHasOverlap(optionEquipments, session.equipment)) return // Set пустой → overlap=false → всё отфильтруется!

// ✅ Правильно: проверяем size перед вызовом overlap
if (optionEquipments.size > 0 && !setHasOverlap(optionEquipments, session.equipment)) return
```

### 4. Мутация исходного массива методом `.reverse()`

В JS/TS массивы передаются по ссылке. Встроенный метод `Array.prototype.reverse()` мутирует исходный массив **in-place** (на месте).

```ts
// ❌ Неправильно: изменяет порядок в оригинальном массиве sessions!
const reversedSessions = sessions.reverse() // Мутирует sessions, вызывающий код получит перевернутый оригинал

// ✅ Правильно: копируем массив через .slice(), а затем разворачиваем копию
const reversedSessions = sessions.slice().reverse() // Оригинальный массив остается нетронутым
```

Функции фильтрации и преобразования данных должны быть **чистыми (pure functions)** и не иметь побочных эффектов.

## Краткий порядок выполнения кода (простыми словами)

Алгоритм `selectData` выполняется в **4 простых этапа**:

### Этап 1: Подготовка и переворот (Разворот)
1. Делается копия исходного массива сессий и полностью переворачивается (`.slice().reverse()`).
   * **Зачем:** Чтобы последнее вхождение каждого пользователя в оригинале оказалось самым первым при последующем обходе.

### Этап 2: Сборка данных (Слияние / Merge)
2. Создается пустой массив `sessionsProcessed` для результатов и вспомогательная `Map` для быстрого поиска уже обработанных пользователей.
3. Циклом обходится перевернутый массив:
   * **Если `merge: true` и пользователя уже видели:** Находим его в `Map` и просто суммируем время тренировки и добавляем новое оборудование в его `Set` (коллекцию уникальных значений). Новый элемент в массив результатов не вставляется.
   * **Если пользователя видим впервые (или `merge: false`):** Клонируем его сессию (превращая массив оборудования в `Set` для защиты от мутаций оригинальных данных и обеспечения быстрой работы), регистрируем в `Map` и добавляем в список результатов.

### Этап 3: Восстановление порядка
4. Полученный список результатов `sessionsProcessed` переворачивается обратно (`.reverse()`).
   * **Зачем:** Чтобы восстановить оригинальный порядок сессий. Теперь объединенная сессия каждого пользователя стоит ровно на месте его последней тренировки.

### Этап 4: Фильтрация и финальный формат
5. Создается `Set` из фильтра по оборудованию (`options.equipment`), чтобы поиск по нему работал мгновенно за $O(1)$.
6. Происходит обход восстановленного массива с отсеиванием сессий:
   * Если не подходит ID пользователя.
   * Если оборудование сессии не пересекается с запрашиваемым.
   * Если общая длительность меньше минимального порога.
7. Сессии, прошедшие все проверки, приводятся к публичному формату: внутренний `Set` оборудования конвертируется обратно в отсортированный массив, и объекты записываются в итоговый массив результатов.

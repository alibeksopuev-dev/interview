# TypeScript: Сужение типов (Type Narrowing), Type Guards и перегрузки функций

Сужение типа (Type Narrowing) — это процесс, при котором TypeScript анализирует структуру кода и уменьшает (делает более конкретным) диапазон возможных типов для переменной в определенной ветке выполнения.

---

## 1. Базовый пример

Если у нас есть тип `string | undefined`, сужение типа позволяет превратить его в чистую строку `string` после проверки:

```typescript
function process(val: string | undefined) {
  if (val !== undefined) {
    // Внутри этого блока тип val сузился до string
    console.log(val.toUpperCase());
  }
}
```

TypeScript умеет делать это автоматически для встроенных конструкций: `typeof`, `instanceof`, `in`, сравнение с `null`/`undefined`, проверка литералов (`val === 'foo'`) и т.д. Это называется **Control Flow Analysis**.

---

## 2. Проблема: сужение внутри функций высшего порядка

Автоматическое сужение работает только в той функции, где написана сама проверка. Если проверку вынести в отдельный колбэк, который передаётся куда-то ещё (например, в `filter`), TypeScript теряет связь между значением колбэка и типом результата:

```typescript
const arr: (string | undefined)[] = ['apple', undefined, 'banana'];
const res = arr.filter(x => x !== undefined);
// Тип res всё ещё (string | undefined)[], хотя мы точно знаем, что undefined там нет
```

Причина — сигнатура `filter` в общем случае выглядит так:

```typescript
filter(callbackFn: (value: T, index: number, array: T[]) => unknown, thisArg?: any): T[];
```

TypeScript видит только тип **возвращаемого значения** колбэка (`unknown`/`boolean`), но не анализирует **тело** колбэка `x => x !== undefined`. Он не может понять, что именно означает эта проверка, поэтому тип результата остаётся неизменным — `T[]`.

---

## 3. Решение: User-Defined Type Guard (`value is S`)

Чтобы TypeScript «поверил» в сужение внутри колбэка, нужно явно объявить функцию как **пользовательский защитник типа (Type Guard)**, используя оператор `is` в возвращаемом типе:

```typescript
const isNotUndefined = (x: string | undefined): x is string => x !== undefined;

const res = arr.filter(isNotUndefined);
// Теперь res: string[]
```

`value is S` — это не просто `boolean`. Это специальная синтаксическая конструкция, которая **утверждает компилятору**: «если функция вернула `true` — то входной аргумент имеет тип `S`». Компилятор доверяет этой аннотации на слово; сама реализация функции рантаймом не проверяется — это чисто подсказка на уровне типов, поэтому важно, чтобы логика внутри действительно соответствовала заявленному утверждению.

Чтобы `filter` мог воспользоваться такой функцией и вывести сузившийся тип массива, у него должна быть отдельная **перегрузка (overload)**:

```typescript
interface Array<T> {
  filter<S extends T>(
    callbackFn: (value: T, index: number, array: T[]) => value is S,
    thisArg?: any,
  ): S[];

  filter(
    callbackFn: (value: T, index: number, array: T[]) => unknown,
    thisArg?: any,
  ): T[];
}
```

Именно так типизирован нативный `Array.prototype.filter` в `lib.es5.d.ts` — см. разбор в [../myFilter/myFilter.md](../myFilter/myFilter.md) (раздел «Подробный разбор типизации»).

## 4. Зачем нужен `S extends T`

Ограничение `S extends T` гарантирует, что `S` может быть только подтипом (или тем же типом), что и `T`, а не произвольным типом.

**Почему это важно:**

1.  **Смысловая корректность.** `filter` не создаёт новых значений — он только отбирает существующие элементы массива. Значит, тип отфильтрованных элементов `S` физически обязан быть подмножеством исходного `T`. Без `extends T` ничто не мешало бы написать guard вида `(x): x is SomeOtherType => true`, и TypeScript вывел бы `SomeOtherType[]` — что абсурдно, ведь `filter` не превращает `string` в никак не связанный тип.

2.  **Типобезопасность.** Без constraint компилятор не сможет проверить, что `S` вообще имеет отношение к `T`, и будет доверять любой аннотации `value is S`, даже нелогичной.

**Пример вывода типа:**

Для `(string | undefined)[]` и guard `(x): x is string => ...`:
*   `T` = `string | undefined`
*   TS проверяет: `string extends (string | undefined)` — выполняется
*   Значит `S = string` — валидная подстановка, результат — `string[]`

Если бы кто-то попытался написать guard `(x): x is number => ...` для того же массива, TS выдал бы ошибку компиляции, потому что `number` не `extends (string | undefined)`.

## 5. Другие способы объявить Type Guard

### 5.1. Функция-предикат (как выше)
```typescript
function isString(x: unknown): x is string {
  return typeof x === 'string';
}
```

### 5.2. `typeof` / `instanceof` инлайн — сужение без явного guard
Работает автоматически внутри самой функции, guard не нужен:
```typescript
function process(x: string | number) {
  if (typeof x === 'string') {
    x.toUpperCase(); // сузилось до string
  }
}
```

### 5.3. Дискриминированные объединения (Discriminated Unions)
Проверка общего поля-литерала («discriminant») сужает весь union:
```typescript
type Shape =
  | { kind: 'circle'; radius: number }
  | { kind: 'square'; side: number };

function area(shape: Shape) {
  if (shape.kind === 'circle') {
    return Math.PI * shape.radius ** 2; // shape сузился до { kind: 'circle'; radius: number }
  }
  return shape.side ** 2;
}
```

### 5.4. `asserts` — Assertion Functions
Не возвращают boolean, а либо ничего не возвращают (значит проверка прошла), либо бросают исключение:
```typescript
function assertIsString(x: unknown): asserts x is string {
  if (typeof x !== 'string') throw new Error('Not a string');
}

function process(x: unknown) {
  assertIsString(x);
  x.toUpperCase(); // после вызова assertIsString тип x сузился до string
}
```

## 6. Итог по narrowing

| Механизм | Где применяется | Пример |
| :--- | :--- | :--- |
| Control Flow Analysis | Прямо в теле функции | `if (val !== undefined) { ... }` |
| `value is S` (Type Predicate) | Функции, передаваемые как колбэки (`filter`, кастомные хелперы) | `(x): x is string => x !== undefined` |
| `asserts x is S` | Функции-валидаторы, кидающие исключение при неудаче | `assertIsString(x)` |
| Discriminated Union | Объекты с общим полем-литералом | `if (shape.kind === 'circle')` |

**Ключевая мысль:** обычная проверка (`x !== undefined`) сужает тип только там, где она физически написана. Как только логика проверки «прячется» внутри отдельной функции-колбэка, TypeScript теряет связь между условием и типом — если явно не объявить эту функцию как Type Guard через `is` или `asserts`.

## 7. Перегрузка функций (Function Overloading)

**Перегрузка функций** — это возможность описать несколько способов вызова одной и той же функции с разными типами аргументов и результатов, используя при этом единую реализацию на уровне JavaScript (перегрузки существуют только в мире типов и не попадают в скомпилированный `.js`).

В TypeScript перегрузка состоит из двух частей:

1.  **Сигнатуры вызова (Overload Signatures)** — публичные интерфейсы функции, которые видит внешний код. Их может быть сколько угодно.
2.  **Сигнатура реализации (Implementation Signature)** — сама функция с телом, которая должна быть совместима со всеми сигнатурами вызова. Внешний код её не видит — TS не позволит вызвать функцию по сигнатуре реализации напрямую, только по одной из объявленных перегрузок.

### Зачем `filter`/`myFilter` две сигнатуры

Метод решает две разные задачи типизации:

1.  **Фильтрация без изменения типа элементов**: `[1, 2, 3]` → оставляем только чётные. Тип элементов не меняется (`number[]` → `number[]`).
2.  **Фильтрация с сужением типа**: `[1, undefined, 2]` → отсеиваем `undefined`. Тип массива должен измениться с `(number | undefined)[]` на `number[]`. Для этого TypeScript должен понять, что колбэк является Type Guard'ом.

```typescript
interface Array<T> {
  // Перегрузка 1: Type Guard — сужает тип
  filter<S extends T>(
    callbackFn: (value: T, index: number, array: T[]) => value is S,
    thisArg?: any,
  ): S[];

  // Перегрузка 2: обычный предикат — тип не меняется
  filter(
    callbackFn: (value: T, index: number, array: T[]) => unknown,
    thisArg?: any,
  ): T[];
}
```

Без перегрузки пришлось бы либо жертвовать сужением типов (разработчикам пришлось бы вручную приводить тип через `as number[]`), либо заставлять всех писать Type Guard, даже если они просто проверяют чётность чисел. Две сигнатуры позволяют TS сам выбрать подходящий вывод типа в зависимости от того, что переда́но в колбэке — это стандартная практика, заимствованная из встроенной `lib.es5.d.ts`.

#### Подробнее: что значит «пришлось бы» в каждом из двух случаев

Разберём отдельно, что было бы, если бы у `filter` была только ОДНА сигнатура вместо двух.

**Сценарий A: только «обычная» сигнатура (без Type Guard)**

Если бы `filter` был объявлен только так:

```typescript
filter(callbackFn: (value: T, index: number, array: T[]) => unknown, thisArg?: any): T[];
```

Результат всегда имеет тип `T[]` — тот же самый тип, что и исходный массив, независимо от того, что делает колбэк:

```typescript
const arr: (number | undefined)[] = [1, undefined, 2];
const res = arr.filter(x => x !== undefined);
// res: (number | undefined)[]  ← TS не сужает, хотя мы точно знаем, что undefined там нет
```

Дальше при попытке использовать `res` как чистый `number[]` компилятор будет ругаться:

```typescript
function sum(nums: number[]) { return nums.reduce((a, b) => a + b, 0); }

sum(res); // ❌ Ошибка: Argument of type '(number | undefined)[]' is not assignable to parameter of type 'number[]'
```

Единственный выход — **вручную обмануть компилятор** через `as`:

```typescript
sum(res as number[]); // ✅ компилируется, но это неявное обещание разработчика "поверь мне"
```

Это и есть та самая ручная привязка типа `as number[]`. Проблема в том, что `as` **ничего не проверяет** — если бы в массиве реально оставался `undefined` (например, из-за бага в предикате), TS всё равно бы пропустил код, и ошибка вылезла бы только в рантайме на `sum`.

**Сценарий B: только сигнатура с Type Guard**

Если бы, наоборот, была объявлена только строгая версия:

```typescript
filter<S extends T>(callbackFn: (value: T, index: number, array: T[]) => value is S, thisArg?: any): S[];
```

Тогда **любой** вызов `filter`, даже самый тривиальный, обязан использовать колбэк с аннотацией `value is S`:

```typescript
const nums = [1, 2, 3, 4];
const evens = nums.filter(x => x % 2 === 0); // ❌ Ошибка!
```

Ошибка возникает потому, что `x % 2 === 0` возвращает обычный `boolean`, а сигнатура требует именно `value is S` — TS не выводит `S` из простого булева выражения, ему нужна явная аннотация типа с `is`. Чтобы это заработало, пришлось бы писать так:

```typescript
function isEven(x: number): x is number { // бессмысленно, S = T
  return x % 2 === 0;
}
const evens = nums.filter(isEven); // только так скомпилируется
```

Это абсурдно раздуто для простой проверки чётности, где тип элементов и так не должен меняться (`number[]` → `number[]`).

**Итог: зачем нужны обе сигнатуры сразу**

Две перегрузки решают обе проблемы одновременно, и TS сам выбирает нужную по тому, что вы написали в колбэке:

| Вызов | Какая перегрузка сработает | Результат |
|---|---|---|
| `nums.myFilter(x => x % 2 === 0)` | 2-я (обычная, `unknown`) | `number[]` — без лишней возни с Type Guard |
| `arr.myFilter((x): x is number => x !== undefined)` | 1-я (`value is S`) | `number[]` — тип реально сужен, никакого `as` |

Так разработчик получает точный вывод типа **только когда он сам явно объявил Type Guard**, а во всех остальных, более частых случаях (проверка чётности, сравнение с константой и т.п.) может писать обычные предикаты без лишнего синтаксиса — и не терять при этом типобезопасность через `as`.

### Более простой пример перегрузки (не связанный с массивами)

Перегрузки — общая концепция TS, не специфичная для `filter`. Классический учебный пример — функция, которая по-разному ведёт себя в зависимости от количества/типа аргументов:

```typescript
// Overload signatures
function makeDate(timestamp: number): Date;
function makeDate(month: number, day: number, year: number): Date;

// Implementation signature (не видна снаружи)
function makeDate(monthOrTimestamp: number, day?: number, year?: number): Date {
  if (day !== undefined && year !== undefined) {
    return new Date(year, monthOrTimestamp, day);
  }
  return new Date(monthOrTimestamp);
}

makeDate(12345678);        // ✅ подходит под 1-ю сигнатуру
makeDate(1, 3, 2024);      // ✅ подходит под 2-ю сигнатуру
makeDate(1, 3);            // ❌ Ошибка: нет сигнатуры с 2 аргументами
```

Обратите внимание: сигнатура реализации (`monthOrTimestamp: number, day?: number, year?: number`) **сама по себе не видна** вызывающему коду — снаружи существуют только две объявленные перегрузки. Поэтому `makeDate(1, 3)` — ошибка, хотя по сигнатуре реализации формально можно было бы вызвать с двумя аргументами.

### Три перегрузки на примере `myReduce`

`reduce`/`myReduce` — более сложный случай, чем `filter`: у него **три** сигнатуры, потому что типизация должна решать сразу две независимые задачи — наличие/отсутствие `initialValue` и его тип относительно типа элементов массива.

```typescript
interface Array<T> {
  // 1. Без initialValue — аккумулятор имеет тот же тип, что и элементы массива
  myReduce(
    callbackFn: (previousValue: T, currentValue: T, currentIndex: number, array: T[]) => T,
  ): T;

  // 2. С initialValue другого типа U — аккумулятор и результат имеют тип U
  myReduce<U>(
    callbackFn: (previousValue: U, currentValue: T, currentIndex: number, array: T[]) => U,
    initialValue: U,
  ): U;

  // 3. Без initialValue, но колбэк работает с union U | T — «страховочная» сигнатура
  myReduce<U>(
    callbackFn: (previousValue: U | T, currentValue: T, currentIndex: number, array: T[]) => U,
  ): U | T;
}
```

**Перегрузка 1** — самый частый случай, когда `initialValue` не передан и тип аккумулятора совпадает с типом элементов:
```typescript
const sum = [1, 2, 3].myReduce((acc, val) => acc + val); // acc: number, результат: number
```
На первой итерации (когда `initialValue` не передан) аккумулятором становится первый элемент массива — значит, его тип обязан совпадать с `T`, других вариантов у компилятора нет.

**Перегрузка 2** — самый частый случай, когда `initialValue` передан и имеет тип, отличный от типа элементов (например, аккумулируем массив чисел в строку или в объект):
```typescript
const str = [1, 2, 3].myReduce((acc, val) => acc + String(val), ''); // acc: string, результат: string
```
Здесь `U` выводится из типа `initialValue` (`''` → `string`), и колбэк, и результат жёстко типизированы как `U`, без примеси `T`.

**Перегрузка 3** — редкий, но важный крайний случай: обобщённая функция-хелпер, которая сама не знает заранее, будет ли `initialValue` передан снаружи, но хочет корректно типизировать `myReduce` в обоих случаях сразу:
```typescript
function sumAny<T extends number>(arr: T[]) {
  return arr.myReduce((acc, val) => acc + val); // acc: number | T
}
```
Тип аккумулятора здесь — union `U | T`, потому что на первом шаге (без явного `initialValue`) аккумулятором становится элемент массива (тип `T`), а на всех последующих шагах — то, что вернул колбэк (тип `U`). Без этой перегрузки такой обобщённый код не скомпилировался бы вообще, потому что TS не смог бы понять, к какой из первых двух сигнатур его отнести.

**Почему нельзя обойтись двумя сигнатурами:** перегрузки 1 и 2 покрывают 95% реальных вызовов и дают точный, не замусоренный union'ами тип. Но они требуют, чтобы `T` и `U` были жёстко зафиксированы на этапе объявления вызова. Перегрузка 3 нужна именно для дженерик-кода (как в `sumAny` выше), где сама вызывающая функция параметризована и не может гарантировать TS, какая из первых двух сигнатур сработает — поэтому ей нужна отдельная, более «мягкая» сигнатура с union-типом.

Как и в случае с `filter`, **порядок сигнатур имеет значение**: более специфичные (1 и 2) идут раньше, а «страховочная» с union (3) — последней, чтобы не перехватывать вызовы, которые и так точно типизируются первыми двумя.

### Как TS выбирает перегрузку

TypeScript проверяет сигнатуры **по порядку сверху вниз** и использует первую подходящую под переданные аргументы. Это критично для порядка объявления в `filter`/`myFilter`.

**Что было бы, если поменять перегрузки местами:**

```typescript
interface Array<T> {
  // Если поставить "обычную" сигнатуру ПЕРВОЙ:
  filter(
    callbackFn: (value: T, index: number, array: T[]) => unknown,
    thisArg?: any,
  ): T[];

  filter<S extends T>(
    callbackFn: (value: T, index: number, array: T[]) => value is S,
    thisArg?: any,
  ): S[];
}
```

Любая функция, возвращающая `boolean`, по структуре подходит и под `unknown` (`boolean` — это подтип `unknown`). Значит TS остановится на первой же подходящей сигнатуре — обычной — и даже колбэк вида `(x): x is string => ...` будет сопоставлен с ней, просто «забыв» про информацию `is string`. До второй, более специфичной перегрузки с Type Guard дело никогда не дойдёт.

**Правило:** более специфичные (узкие, «дорогие» для вывода) перегрузки нужно объявлять выше, более общие — ниже. Именно поэтому в объявлении `filter`/`myFilter` перегрузка с `value is S` идёт первой.

## 8. Declaration Merging: как безопасно добавить метод в `Array.prototype`

Чтобы TypeScript знал о существовании кастомного метода (например, `myFilter`) на массивах, используется **Declaration Merging** — механизм, при котором несколько объявлений с одинаковым именем объединяются в одно:

```typescript
export {}; // делает файл модулем для изоляции типов

declare global {
  interface Array<T> {
    myFilter<S extends T>(
      callbackFn: (value: T, index: number, array: Array<T>) => value is S,
      thisArg?: any,
    ): Array<S>;

    myFilter(
      callbackFn: (value: T, index: number, array: Array<T>) => unknown,
      thisArg?: any,
    ): Array<T>;
  }
}
```

### Что такое Declaration Merging в общем виде

Declaration Merging — не специфика `Array`, а общий механизм TS: если в одной области видимости объявить **два `interface`** с одинаковым именем, компилятор не выдаёт ошибку (как было бы с `type`), а объединяет их члены в одно общее описание:

```typescript
interface Box {
  width: number;
}
interface Box {
  height: number;
}
// Итоговый Box эквивалентен:
// interface Box { width: number; height: number; }

const b: Box = { width: 10, height: 20 }; // нужны оба поля
```

С `type Box = { width: number }` так сделать нельзя — повторное объявление `type Box = { height: number }` в той же области видимости — ошибка компиляции («Duplicate identifier»). Это одно из ключевых практических отличий `interface` от `type`.

Именно это свойство используется, чтобы добавить `myFilter` в существующий `Array<T>`: TypeScript берёт наше объявление `interface Array<T> { myFilter(...): ...; }` из `myFilter.md` и **сливает** его с оригинальным `interface Array<T> { filter(...); map(...); ... }`, который уже объявлен в `lib.es5.d.ts`. В результате у типа `Array<T>` появляется новый метод, как будто он был в библиотеке изначально.

### Построчный разбор конструкции

```typescript
export {}; // делает файл модулем для изоляции типов

declare global {
  interface Array<T> {
    myFilter<S extends T>(
      callbackFn: (value: T, index: number, array: Array<T>) => value is S,
      thisArg?: any,
    ): Array<S>;

    myFilter(
      callbackFn: (value: T, index: number, array: Array<T>) => unknown,
      thisArg?: any,
    ): Array<T>;
  }
}
```

*   **`interface Array<T> { ... }`** — благодаря Declaration Merging «дописывает» новый метод к встроенному интерфейсу `Array<T>` из `lib.es5.d.ts`, не трогая исходный файл библиотеки и не создавая копию типа.
*   **`declare global { ... }`** — нужен, чтобы расширение применялось к **глобальному** интерфейсу `Array`, видимому во всём проекте, а не к какому-то локальному типу с тем же именем. Без `declare global` объявление `interface Array<T>` внутри модуля создало бы отдельный, изолированный тип `Array`, который заслонял бы глобальный только в пределах этого файла — и метод `myFilter` не был бы виден нигде за его пределами.
*   **`export {};`** — превращает файл в **модуль** (ES Module) вместо глобального скрипта.
    *   Дело в том, что `declare global` разрешено использовать только внутри модуля — TypeScript требует явного `import`/`export`, чтобы считать файл модулем.
    *   Если файл не модуль (нет ни одного `import`/`export`), TS трактует его как global-скрипт, и любое объявление `interface Array<T>` в нём и так автоматически модифицирует глобальный тип напрямую — но при этом рискует конфликтовать с объявлениями из других таких же global-скриптов в проекте.
    *   `export {}` — это «пустой» экспорт, который ничего реально не экспортирует, но формально делает файл модулем ради изоляции его локальных типов/переменных, и именно поэтому далее требуется `declare global`, чтобы явно "пробить" эту изоляцию только для одного нужного интерфейса.

### Типы отдельно, реализация отдельно

Важно понимать, что `declare global { interface Array<T> {...} }` — это **только тайпчекинг**, он не порождает никакого рантайм-кода. Реальная реализация метода задаётся отдельно, обычным присваиванием функции в `Array.prototype`:

```typescript
Array.prototype.myFilter = function <T>(
  this: T[],
  callbackFn: (value: T, index: number, array: T[]) => unknown,
  thisArg?: any,
): any[] {
  // ...
};
```

Если объявить типы (`declare global`), но забыть реализацию (`Array.prototype.myFilter = ...`) — TS не выдаст ошибку компиляции (он не проверяет, что у объявленного метода есть реальная реализация в рантайме), но в браузере вызов `[].myFilter(...)` упадёт с `TypeError: ... is not a function`. И наоборот: если написать реализацию без `declare global`, TS будет ругаться на каждый вызов `arr.myFilter(...)`, потому что не знает о существовании такого метода в типе `Array<T>`.

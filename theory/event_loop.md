# Event Loop & Throttle: Полное современное руководство

В данном руководстве объединены фундаментальные основы **Event Loop (Цикла событий)** в браузерах и Node.js по актуальным стандартам HTML5/ECMAScript, а также подробный разбор работы паттерна **Throttle** на уровне рантайма.

---

# ЧАСТЬ 1. Современный Event Loop: Стандарты, очередезация и приоритеты

**Event Loop (Цикл событий)** — это бесконечный цикл, который координирует выполнение скриптов, обработку событий, выполнение задач, обработку микрозадач и обновление графического интерфейса пользователя.

## 1. Схема жизненного цикла Event Loop в браузере

Современный цикл событий в браузере обрабатывает задачи различного приоритета и выглядит следующим образом:

```
┌────────────────────────────────────────────────────────┐
│                      CALL STACK                        │
│             (Синхронное выполнение, LIFO)              │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│                   MICROTASK QUEUE                      │
│ (Promise, queueMicrotask, MutationObserver. FIFO)      │
│ * Выполняется до полного опустошения после каждой      │
│   задачи из Call Stack *                               │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│                  RENDERING PIPELINE                    │
│ (rAF -> Recalculate Style -> Layout -> Paint)          │
│ * Выполняется по расписанию экрана (~16.6мс при 60Гц)  │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│                   MACROTASK QUEUE                      │
│ (Tasks: setTimeout, events, postMessage, FIFO)         │
│ * За один тик извлекается ровно ОДНА макрозадача *     │
└────────────────────────────────────────────────────────┘
```

### Архитектурные компоненты:
1. **Call Stack (Стек вызовов)**: Синхронный стек выполнения инструкций. JS однопоточен, поэтому пока стек не пуст, ни одна другая задача не может начаться.
2. **Microtask Queue (Очередь микрозадач)**:
   - Обладает высочайшим приоритетом исполнения.
   - Очередь очищается **полностью** (включая микрозадачи, добавленные в процессе очистки) перед тем, как Event Loop перейдет к следующему шагу (рендерингу или макрозадаче).
3. **Macrotask Queue (Очередь макрозадач / Tasks)**:
   - Задачи, поступающие от внешних API (клики, таймеры, сетевые ответы).
   - За один тик Event Loop выполняет **ровно одну** макрозадачу из очереди, после чего сразу переходит к очистке очереди микрозадач.
4. **Rendering Pipeline (Конвейер рендеринга)**:
   - Запускается параллельно с частотой обновления экрана (например, 60Hz, 120Hz).
   - Не привязан жестко к макрозадачам: браузер может пропустить рендер, если экран не обновляется, или объединить несколько макрозадач перед отрисовкой кадра.

## 2. Анатомия очередей задач

### Микрозадачи (Microtasks)
Спецификация предписывает выполнять микрозадачи сразу после того, как стек вызовов освобождается.
* Источники микрозадач:
  - `Promise.prototype.then() / catch() / finally()`
  - Ключевое слово `await` (транспилируется в промисы)
  - `queueMicrotask(() => { ... })` — современный стандартный метод ручного планирования микрозадачи
  - `MutationObserver` (отслеживание изменений DOM)

### Макрозадачи (Tasks / Macrotasks)
* Источники макрозадач:
  - Парсинг HTML-документа (первоначальный запуск скрипта)
  - Колбэки таймеров (`setTimeout`, `setInterval`)
  - Пользовательские события ввода (клик, движение мыши, скролл, ввод текста)
  - События сети (колбэки от `fetch`, `XMLHttpRequest`, `WebSocket`)
  - Межпоточные сообщения (`postMessage`, `MessageChannel`)

### Специальные очереди визуализации
* **`requestAnimationFrame` (rAF)**:
  - Выполняется строго **перед** шагом рендеринга (Style, Layout, Paint).
  - Подходит для любых манипуляций с DOM, влияющих на геометрию или стили элементов.
* **`requestIdleCallback` (rIC)**:
  - Выполняется в периоды «простоя» браузера, когда в очередях нет срочных макро- или микрозадач, а до следующего кадра рендеринга осталось время.

### Сетевые запросы (`fetch`, `axios`): Макро- или Микрозадачи?
Сетевой запрос проходит через несколько стадий:
1. **Инициация запроса**: Вызов `fetch()` происходит **синхронно** в Call Stack. Запрос передается в Web APIs (сетевой поток браузера) и выполняется параллельно.
2. **Получение ответа**: Когда сервер возвращает ответ, сетевой поток браузера генерирует событие завершения запроса и помещает его в **очередь макрозадач (Macrotask Queue)**.
3. **Разрешение Promise**: При выполнении этой макрозадачи связанный Promise меняет состояние на `fulfilled` (или `rejected`).
4. **Обработка данных**: Код в `.then()` или инструкции, идущие сразу после `await`, помещаются в **очередь микрозадач (Microtask Queue)** и выполняются с наивысшим приоритетом сразу после очистки текущей макрозадачи.

*Резюме: Само событие получения ответа из сети — это макрозадача, а обработка его результата через `Promise` / `await` — это микрозадача.*

### Сетевые запросы (`fetch`, `axios`): Макро- или Микрозадачи?

Короткий ответ: **Сам сетевой ответ от браузера приходит как макрозадача (macrotask), но обработка его результата через `Promise` / `await` выполняется в очереди микрозадач (microtasks).**

#### Подробный разбор по этапам (Lifecycle сетевого запроса)

Рассмотрим классический код:
```javascript
console.log('Start'); // 1. Синхронно

fetch('https://api.example.com/data')
  .then(res => res.json())
  .then(data => console.log('Data received', data)); // 3. Где это выполнится?

console.log('End'); // 2. Синхронно
```

##### Этап 1: Инициация запроса (Синхронный код)
Когда движок встречает вызов `fetch(...)`, он выполняет его **синхронно** в Call Stack.
1. `fetch` передает управление браузерному окружению (**Web APIs**), которое отвечает за работу с сетью.
2. Сам JavaScript-поток освобождается (идет дальше и выводит `'End'`), а сетевой запрос выполняется параллельно на уровне операционной системы/браузера.

##### Этап 2: Получение ответа от сервера (Макрозадача / Macrotask)
Когда сервер присылает ответ:
1. Сетевой поток браузера получает данные.
2. Браузер должен сообщить об этом JavaScript-движку. Для этого он помещает внутреннее сетевое событие (колбэк успешного завершения запроса) в **очередь макрозадач (Macrotask Queue)**.
3. Когда подходит очередь этой макрозадачи, она попадает в Call Stack. Внутри этой макрозадачи происходит изменение состояния (разрешение) связанного Промиса: `Promise` переходит из состояния `pending` в `fulfilled`.

##### Этап 3: Обработка результата в JS (Микрозадача / Microtask)
1. Разрешение (resolve) промиса автоматически планирует выполнение всех привязанных обработчиков (`.then()`, `.catch()`, `.finally()` или код после `await`) в **очередь микрозадач (Microtask Queue)**.
2. Сразу после завершения текущей макрозадачи (из Этапа 2) Event Loop видит, что появились микрозадачи, и **полностью очищает очередь микрозадач**.
3. Наш код `.then(res => ...)` или код, идущий сразу за `await fetch(...)`, выполняется именно как **микрозадача**.

#### Резюме для собеседования

1. **Событие получения данных из сети (Network Event)** — это **макрозадача**. Браузер не может обработать его посреди синхронного кода, он ставит его в общую очередь задач (вместе с кликами и таймерами).
2. **Обработка данных (код внутри `.then` или после `await`)** — это **микрозадача**. Как только промис разрешился (что произошло внутри сетевой макрозадачи), колбэки обработчиков выполняются с наивысшим приоритетом в очереди микрозадач.

## 3. Современное управление приоритетами: `Scheduler.postTask()`

В современных браузерах появился стандартный API планирования задач с приоритетами — **`Scheduler.postTask`** (доступен через глобальный объект `scheduler`). Он позволяет обходить стандартное поведение очередей и явно задавать приоритет выполнения:

```javascript
// Пример планирования задач с разными приоритетами
scheduler.postTask(() => console.log('Высокий приоритет для UI'), { priority: 'user-blocking' });
scheduler.postTask(() => console.log('Обычный приоритет'), { priority: 'user-visible' });
scheduler.postTask(() => console.log('Низкий приоритет для аналитики'), { priority: 'background' });
```

### Доступные уровни приоритетов:
1. `'user-blocking'`: Задачи, критичные для интерактивности интерфейса (например, реакция на ввод пользователя). Блокируют рендер.
2. `'user-visible'`: Задачи по умолчанию (например, рендеринг данных после сетевого запроса).
3. `'background'`: Задачи с наименьшим приоритетом (логирование, отправка метрик, предзагрузка данных).

## 4. Различия между браузером и Node.js

Node.js использует библиотеку асинхронного ввода-вывода **libuv**, и его Event Loop имеет другую структуру фаз по сравнению с браузером.

```
┌────────────────────────────────────────────────────────┐
│                        TIMERS                          │
│             (setTimeout, setInterval)                  │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│                   PENDING CALLBACKS                    │
│      (Отложенные системные операции ввода-вывода)      │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│                     IDLE, PREPARE                      │
│             (Внутреннее использование)                 │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│                         POLL                           │
│        (Ожидание новых событий ввода-вывода / I/O)     │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│                         CHECK                          │
│                    (setImmediate)                      │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│                    CLOSE CALLBACKS                     │
│               (socket.on('close'), ...)                │
└────────────────────────────────────────────────────────┘
```

### Основные отличия Node.js от браузера:
1. **Отсутствие рендеринга**: В Node.js нет фазы визуализации (Style, Layout, Paint, rAF).
2. **`process.nextTick()`**:
   - Это не микрозадача, а особый тип высокоприоритетного колбэка.
   - Очередь `nextTick` обрабатывается **сразу** после текущей синхронной операции в Call Stack, даже **до** стандартной очереди микрозадач (`Promise.then`).
3. **`setImmediate`**:
   - Специальный таймер, выполняющийся строго в фазе **Check**, сразу после фазы опроса **Poll** (где обрабатывается большинство событий ввода-вывода).

# ЧАСТЬ 2. Взаимодействие паттерна Throttle с Event Loop

Разберем, как выполнение дросселируемой (`throttled`) функции ложится на описанные структуры Event Loop.

## 1. Код базовой реализации Throttle

```typescript
function throttle<T extends (...args: any[]) => void>(func: T, limit: number): T {
  let inThrottle = false;

  return function(this: any, ...args: any[]) {
    if (!inThrottle) {
      // 1. Немедленный вызов оригинальной функции (Leading Edge)
      func.apply(this, args);
      
      // 2. Блокировка вызовов
      inThrottle = true;

      // 3. Планирование снятия блокировки через `limit` мс
      setTimeout(() => {
        inThrottle = false;
      }, limit);
    }
  } as T;
}
```

### Сравнение реализаций: Академическая vs Практическая (из проекта)

При сопоставлении кода выше с продакшн-реализацией в [throttle.ts](file:///Users/alibek/WebstormProjects/interview/throttle/throttle.ts) заметны ключевые различия в типизации и внутренней структуре:

#### 1. Различие в стратегии типизации (Generics)
* **Академический вариант (`throttle_event_loop.md`)**:
  `T extends (...args: any[]) => void`
  Здесь дженерик `T` привязан к сигнатуре всей функции. При возврате используется принудительное приведение типов через `as T`. 
  *Минус*: Это принудительно заставляет возвращаемую функцию утверждать, что она возвращает тот же тип, что и `func` (хотя вызов `throttled()` при пропуске возвращает `undefined`), а также может терять автодополнение для параметров в старых версиях TS.
* **Практический вариант (`throttle.ts`)**:
  `T extends any[]` и `ThrottleFunction<T> = (this: any, ...args: T) => any`
  Здесь дженерик `T` типизирует **кортеж аргументов** (tuple), а не саму функцию.
  *Плюс*: Это обеспечивает стопроцентно точную типизацию параметров функции через Rest-параметры `...args: T` и чистое наследование контекста `this`, избавляя от небезопасного приведения типов `as T`.

#### 2. Различие в логике управления блокировкой (Early Return vs Conditional Block)
* **Академический вариант**: Использование условного ветвления `if (!inThrottle) { ... }`. Вся основная логика обернута внутрь блока ветвления.
* **Практический вариант**: Паттерн **Early Return (быстрый возврат)**:
  ```typescript
  if (shouldThrottle) {
    return;
  }
  // Основная логика выполняется на верхнем уровне
  ```
  Это делает код более читаемым, уменьшая уровень вложенности (nesting) и упрощая отладку.

## 2. Пошаговый жизненный цикл в Event Loop (Пример)

Допустим, мы установили интервал дросселирования `limit = 100` мс. Пользователь генерирует события в моменты: `t = 0`, `t = 20`, `t = 50`, `t = 110`.

### Фаза 1: Событие при `t = 0` (Запуск)
1. Браузер переносит обработчик первого события скролла в **Call Stack**.
2. Поскольку `inThrottle === false`, выполняется оригинальный `updateUI()` (синхронно).
3. Переменная `inThrottle` меняет значение на `true`.
4. Вызывается `setTimeout(unlock, 100)`. Этот вызов регистрируется в **Web APIs**. Фоновый поток браузера начинает обратный отсчет.
5. Обработчик завершается и удаляется из **Call Stack**. Стек пуст.

### Фаза 2: Игнорирование при `t = 20` и `t = 50`
1. Новое событие добавляет обработчик `throttledScroll` в Call Stack.
2. Проверяется условие `if (!inThrottle)`. Поскольку `inThrottle === true`, выполнение игнорируется.
3. Функция мгновенно выходит из Call Stack без вызова оригинальной логики.

### Фаза 3: Снятие блокировки при `t = 100`
1. По завершении 100 мс фоновый поток Web APIs помещает колбэк таймера `() => { inThrottle = false; }` в **Macrotask Queue**.
2. На следующем тике Event Loop проверяет, пуст ли Call Stack и очередь микрозадач. Если они свободны, колбэк забирается в **Call Stack**.
3. Синхронно выполняется `inThrottle = false`, снимая ограничение.
4. Колбэк удаляется из Call Stack.

# ЧАСТЬ 3. Тест на знание Event Loop (Классический вопрос на интервью)

Для закрепления понимания приоритетов очередей разберите порядок вывода следующих инструкций:

```javascript
console.log('1: Sync start');

setTimeout(() => {
  console.log('2: setTimeout (macrotask)');
}, 0);

Promise.resolve().then(() => {
  console.log('3: Promise 1 (microtask)');
}).then(() => {
  console.log('4: Promise 2 (microtask)');
});

queueMicrotask(() => {
  console.log('5: queueMicrotask (microtask)');
});

requestAnimationFrame(() => {
  console.log('6: rAF (animation)');
});

console.log('7: Sync end');
```

### Правильный порядок вывода:
1. `1: Sync start` — Синхронный код выполняется первым.
2. `7: Sync end` — Синхронный код выполняется до конца.
3. `3: Promise 1 (microtask)` — Микрозадачи выполняются сразу после очистки Call Stack.
4. `5: queueMicrotask (microtask)` — Помещено в очередь микрозадач и выполняется до перехода к макрозадачам.
5. `4: Promise 2 (microtask)` — Результат чейнинга `.then()`, создавший новую микрозадачу, успевает выполниться в текущем цикле очистки микрозадач.
6. `6: rAF (animation)` — Выполняется перед обновлением экрана (если оно запланировано).
7. `2: setTimeout (macrotask)` — Попадает в очередь макрозадач и выполняется на следующем тике Event Loop.
